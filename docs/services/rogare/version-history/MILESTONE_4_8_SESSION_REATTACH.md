# Lumen Rogare M4.8 — Session Reattachment

## Purpose

Prevent a Rogare page reload or Servire pop-out/re-embed transition from silently preparing a new logical conversation while an existing Rogare session remains active.

## Behaviour

- Rogare now records the currently attached logical session in Rogare server state when `/api/console/session/start` succeeds.
- Successful conversational turns are retained as transient Rogare presentation history so another UI instance can redraw the conversation. This history is not used as model context; the Lumen/Moderari session remains authoritative for conversational continuity.
- On page load the UI calls `/api/console/session/active`. If a session is attached, Rogare reattaches to that session, restores the provider-binding display, redraws the known user/assistant turns, and primes the existing Pontis backchannel cursor.
- `prepareNewSession()` is now used only when no active session exists or when the operator explicitly requests **New Session**.
- **New Session** calls `/api/console/session/detach` before preparing the next autogenerated name. Detaching does not delete Pontis/Moderari context or the retained presentation history.

## Architectural boundary

The added transcript is presentation state only. It does not replace, reconstruct, or feed model context. Session continuity remains identified by the original `session-rogare-*` ID and is owned by the existing Lumen stack.
