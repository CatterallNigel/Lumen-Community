# Lumen Rogare Architecture

## Overview

Rogare is the conversational client for the Lumen stack.

It has a single responsibility:

**Provide the human conversational surface without owning model orchestration, tool execution, or conversational context.**

Rogare presents conversations, session controls, progress information, and operator-facing interaction. The authoritative conversation state remains within the Lumen stack.

---

# Architectural Position

```text
                     Servire
                        │
                 Embedded / Pop-out
                        │
                        ▼
                   Lumen Rogare
                        │
                  OpenAI-compatible
                       HTTP
                        │
                        ▼
                   Lumen Pontis
                  ┌─────┴─────┐
                  │           │
                 ACP         HTTP
                  │           │
                  ▼           ▼
                  Pi   Vestigare → Repetere → Moderari
                  ▲                         │
                  └──────── tool path ──────┘
                                            │
                                            ▼
                                         Provider
```

Rogare is a client of Pontis. It does not communicate directly with Pi, Moderari, or the model provider.

---

# Conversational Responsibility

Rogare owns the user-facing conversational experience.

It is responsible for:

- starting and naming Rogare sessions;
- accepting user prompts;
- presenting assistant responses;
- displaying session and provider state;
- presenting backchannel heartbeat/progress information;
- exposing operator controls appropriate to the conversational client;
- supporting embedded and pop-out presentation through Servire.

Rogare does not own:

- model selection or model lifecycle;
- tool execution;
- ACP protocol management;
- model orchestration;
- authoritative conversational context;
- replay, trace, assessment, or provenance semantics.

---

# Session Model

A Rogare session has a logical Lumen session identifier, normally of the form:

```text
session-rogare-<timestamp>
```

This identifier represents the logical client conversation and is propagated through Pontis into the Lumen stack.

Pontis may maintain a separate ACP session for Pi. The ACP session is deliberately distinct from the Rogare/Lumen session because it belongs to a different protocol plane.

Rogare does not need to understand or manage the ACP session identifier.

The architectural relationship is:

```text
Rogare/Lumen session
        │
        ▼
      Pontis
        │
        ├── logical Lumen session identity
        │
        └── associated ACP/Pi session identity
```

Pontis owns the correlation between these identities.

---

# Conversation Context

Rogare is not the authoritative store of conversational understanding.

The Lumen/Moderari session context carries the conversation required for model continuity. Rogare may retain presentation state sufficient to redraw an existing conversation when its UI is recreated, but that presentation state is not fed back to the model as a second source of context.

This distinction is important:

**Rogare displays the conversation; Lumen owns the conversational context.**

---

# Session Reattachment

Rogare can be displayed inside Servire or in a separate pop-out window.

Changing presentation must not create a new logical conversation.

On UI load Rogare therefore follows this lifecycle:

```text
Rogare UI loads
      │
      ├── active session exists
      │       │
      │       ├── reattach to existing session
      │       ├── restore provider/session presentation
      │       └── redraw the existing conversation
      │
      └── no active session
              │
              └── prepare a new autogenerated session
```

`New Session` is the explicit conversation boundary. It detaches the current UI and prepares a new logical Rogare session without requiring the previous Lumen context to be destroyed.

---

# Provider Session Establishment

Starting a Rogare session causes Pontis to establish the provider/tool-side session required for the conversation.

The provider bootstrap may involve:

1. creation of an ACP session with Pi;
2. selection of the configured provider/model;
3. a provider initialization request through the Lumen model path;
4. completion of the bootstrap before Rogare marks the session ready.

Cold model startup can therefore take substantially longer than a normal warm session start.

Rogare presents this as a lifecycle operation rather than a normal conversational request.

---

# Backchannel Progress

Long-running model requests can produce heartbeat and progress events in Moderari.

The path is:

```text
Moderari
    │
    │ heartbeat / progress
    ▼
Pontis backchannel
    │
    │ retained session events
    ▼
Rogare polling
    │
    ▼
Operator UI
```

Rogare uses a polling backchannel rather than requiring a persistent client event stream.

For an active conversational request Rogare presents:

- request elapsed time;
- model/provider progress text supplied by Moderari;
- estimated context usage when available;
- heartbeat state;
- recency of the most recently received heartbeat.

The local request elapsed time and Moderari progress elapsed time may legitimately differ because they measure different portions of the operation.

During provider/session establishment Rogare currently presents lifecycle elapsed time. Bootstrap heartbeat events can exist in the stack even when the UI is not yet polling them.

---

# Tool Interaction

Rogare does not implement tools.

When a Rogare conversation requires tools:

```text
Rogare
   │
   ▼
Pontis
   │
   ▼
Moderari / model reasoning
   │
   │ tool requirement
   ▼
Pontis ACP bridge
   │
   ▼
Pi
   │
   ▼
Tool
```

Pontis provides the protocol bridge and session correlation. Rogare remains unaware of the internal ACP mechanics.

---

# Relationship to Servire

Servire is the operational control surface.

Rogare is the conversational client.

Servire:

- starts and monitors Rogare;
- embeds Rogare in the unified workspace;
- can expose Rogare as a pop-out workspace;
- manages Rogare as a Lumen service.

Rogare remains independently responsible for its conversational UI and session attachment semantics.

Moving between Servire's embedded and pop-out presentation must not alter the underlying logical conversation.

---

# Runtime Responsibilities

Rogare owns:

- conversational UI;
- user prompt submission;
- assistant-response presentation;
- logical session naming and attachment;
- session reattachment presentation;
- heartbeat/progress presentation;
- operator-facing conversational controls;
- Rogare runtime health and logging.

Rogare does not own:

- authoritative Lumen context;
- ACP sessions;
- tool execution;
- model lifecycle;
- provider discovery/control;
- behavioural orchestration;
- trace recording;
- replay execution;
- assessment.

---

# Architectural Invariants

Rogare is a client, not an orchestrator.

It must not become the authoritative owner of conversational context merely because it renders the transcript.

UI recreation, embedding, pop-out, or browser reload must not implicitly create a new logical conversation when an active Rogare session can be reattached.

A new conversation begins only through an explicit session boundary such as `New Session`.

Rogare may present Lumen operational state, but it must not duplicate the responsibilities of Pontis, Moderari, Praebere, or Pi.

This separation allows Rogare to evolve as the native Lumen conversational experience without coupling the Lumen reasoning architecture to a particular user interface.
