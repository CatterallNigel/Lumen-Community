# Lumen Pontis M6.2 — Rogare Session Bootstrap

## Objective

Add the smallest possible Rogare session bootstrap on top of the proven M6 ACP→HTTP provider
re-entry mechanism without changing the Replay-dependent provider re-entry path.

## Implemented

- Recognise exact `\obt rogare start` on `/v1/chat/completions`.
- Require a stable Lumen session identity.
- Reuse `x-lumen-cwd` / existing continuation context for provider attachment.
- Attach or reuse the Pi ACP session through `PontisSessionService.deliver`.
- Send a neutral no-tool bootstrap prompt to Pi.
- Allow Pi HTTP traffic generated by that ACP prompt to re-enter through the unchanged
  transparent M6 branch.
- Return a structured `pontis_control` readiness result to the original caller.
- Do not extract or translate Pi's tool catalogue in Pontis.
- Preserve the Replay provider re-entry invariant, including when re-entry payload text happens
  to contain `\obt rogare start`.

## Automated verification in delivered package

- `pytest`: 50 passed.
- Added tests for Rogare bootstrap interception, stable-session enforcement and Replay-safe
  provider re-entry precedence.
- Ruff/mypy were not available in the packaging environment and must be run in the normal local
  development environment.

## Live acceptance test

1. Start the normal Lumen stack including Pontis and Pi ACP adapter.
2. Send `\obt rogare start` with a stable `x-lumen-session-id` and useful `x-lumen-cwd`.
3. Confirm Pontis logs ACP session creation/reuse and `Sending ACP prompt`.
4. Confirm Pi performs HTTP `/v1/chat/completions` re-entry.
5. Confirm Pontis logs `HTTP provider re-entry detected during active ACP prompt`.
6. Confirm the re-entry traverses Vestigare, Repetere and Moderari.
7. Confirm Moderari receives Pi's normal tool declarations/system context handling.
8. Confirm the original request returns `pontis_control.status=ready`.
9. Re-run a known Replay fork/tool case and confirm its ACP→HTTP behavior is unchanged.
