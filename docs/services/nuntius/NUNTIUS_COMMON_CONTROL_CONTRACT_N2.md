# Nuntius Common Control Contract — N2

**Date:** 2026-08-25  
**Status:** Agreed Design  
**Scope:** Pontis, Nuntius, Servire, Repetere, Moderari, Praebere  
**Purpose:** Define the common Lumen `\obt` control contract before implementation.

---

## 1. Command Taxonomy

The Lumen control-command taxonomy remains:

```text
\obt <service> <command> [arguments...]
```

Examples:

```text
\obt repetere start <replay-id>
\obt moderari pass-through
\obt praebere models
\obt praebere select model <model>
```

The service token identifies the authoritative destination service.

---

## 2. Nuntius Parsing Responsibility

Nuntius remains deliberately lightweight, but it does understand two parts of the control language:

1. the **service token** immediately following `\obt`, used to route the request; and
2. the reserved operation **`select`**, which has control-plane semantics because a successful selection changes shared state and may require listener updates.

For:

```text
\obt praebere select model qwen2.5-coder:14b
     ^^^^^^^^^ ^^^^^^
     service   reserved operation
```

Nuntius understands:

```text
service = praebere
operation = select
```

Everything after `select` remains opaque domain content and is interpreted only by the destination service.

For a non-`select` command such as:

```text
\obt praebere models
```

Nuntius uses only the service token for routing and does not interpret `models`.

Nuntius must not understand model semantics, Replay semantics, prompt semantics, provider semantics, or other domain behaviour.

---

## 3. Common Control Endpoint

Every Nuntius-addressable service exposes:

```text
POST /control/obt
```

Pontis is a boundary exception because it may consume commands it owns locally before Nuntius is involved.

---

## 4. Pontis-Owned Commands

The existing command:

```text
\obt rogare start
```

remains Pontis-owned.

It must not be routed:

```text
Rogare -> Pontis -> Nuntius -> Pontis
```

The rule is:

> **Pontis consumes commands it owns. Other client-originated `\obt` commands are routed to Nuntius.**

Pontis does not determine the owner of non-Pontis commands beyond extracting the destination service token.

---

## 5. Common Request Envelope

The common control request contains:

```text
request_id
timestamp
session_id
origin
command
```

### `request_id`

A unique identifier for one control transaction.

It is mandatory.

### `timestamp`

UTC timestamp generated by the originator.

It remains unchanged for the lifetime of the transaction and supports timing diagnostics.

### `session_id`

The existing Lumen/client session identity.

It is preserved through the control path and may be `null` where no session context exists.

Nuntius must not introduce a second session identity mechanism.

### `origin`

Identifies the originator using canonical values such as:

```text
client
servire
rogare
repetere
moderari
praebere
```

`origin` is identity/provenance. The synchronous request path remains the normal mechanism for returning the authoritative result.

### `command`

Contains the complete, unchanged `\obt ...` command.

Example:

```json
{
  "request_id": "8cf4b2e2-...",
  "timestamp": "2026-08-25T19:33:42.123Z",
  "session_id": "session-123",
  "origin": "client",
  "command": "\\obt praebere select model qwen2.5-coder:14b"
}
```

---

## 6. Servire Registry

Servire is authoritative for the active control-plane topology.

Because the owning service is already encoded in the `\obt` command, Servire does not need to maintain a catalogue of every command a service understands.

A service entry is intentionally lightweight:

```yaml
praebere:
  endpoint: http://praebere:11431/control/obt
  obt_enabled: true
  listeners:
    - moderari
    - rogare
```

The registry needs to represent at minimum:

```text
service name
endpoint
obt_enabled
active state
listeners[]
```

Nuntius obtains this registry from Servire and maintains the active routing view in memory.

---

## 7. Query Behaviour

Ordinary query/request commands return only to the originator.

Example:

```text
\obt praebere models
```

Flow:

```text
originator
    |
    v
Pontis / internal caller
    |
    v
Nuntius
    |
    v
Praebere
    |
    | model list
    v
Nuntius
    |
    v
originator
```

No additional listener notification occurs merely because Praebere has configured listeners.

If Rogare originated the request, Rogare receives the normal response.

If an external client originated the request, the external client receives the normal response.

---

## 8. Reserved `select` Semantics

`select` is a reserved Nuntius control-language operation.

The syntax is:

```text
\obt <service> select ...
```

A successful `select` represents a state-changing selection.

Nuntius does not understand what is being selected.

After the owning service successfully applies the selection, Nuntius:

1. returns the authoritative response to the originator; and
2. distributes the successful response body to the listeners configured for that service by Servire.

Example:

```text
\obt praebere select model X
```

Flow:

```text
                   +--> originator
                   |
Praebere -> Nuntius
                   |
                   +--> Moderari
                   |
                   +--> Rogare
```

If a configured listener is already the originator, Nuntius must not send the same result to that service twice.

---

## 9. Response Body

Services should use one response representation for both human-facing and machine-facing consumers.

A successful response body may contain:

```json
{
  "message": "Model selected: qwen2.5-coder:14b",
  "data": {
    "provider": "ollama",
    "model": "qwen2.5-coder:14b"
  }
}
```

### `message`

Human-readable representation.

Suitable for:

- command-line clients;
- external OpenAI-compatible clients;
- simple UI display.

### `data`

Optional machine-readable structured information.

Suitable for:

- Moderari;
- Rogare;
- other Lumen listeners.

Nuntius treats both fields as opaque response content.

Nuntius does not parse or interpret `data`.

A successful command with nothing useful to return may still use:

```text
200 OK
```

with no body.

---

## 10. Response Semantics

The existing Nuntius response contract remains:

```text
200, no body
    successful execution

200 + body
    successful execution/query with returned information

204
    command not handled

4xx / 5xx
    recognised command failure

504
    authoritative outcome not confirmed before timeout
```

Every solicited command produces one terminal outcome for its originator.

Success must never be inferred from silence.

A listener-delivery failure does not change an already successful authoritative owner result. It is recorded as Nuntius diagnostic evidence.

---

## 11. External Client Representation

For an external OpenAI-compatible client, Pontis converts the control response into an ordinary assistant response.

Example:

```text
user:
\obt praebere models

assistant:
Available models:
- qwen2.5-coder:14b
- gemma3:4b
```

No special external message role is required.

Internally, the control response remains structured.

Pontis owns the translation between the internal control response and the external OpenAI-compatible assistant response.

---

## 12. Pontis Control-History Sanitation

External clients own and retain their own conversational history.

A later ordinary request may therefore contain a previous synchronous control exchange:

```text
user:      \obt praebere models
assistant: Available models...
user:      Now answer my next question...
```

Pontis must sanitise this history before forwarding the normal request into the model execution path.

The deterministic rule is:

> **A `user` message beginning with `\obt` and its immediately following `assistant` message form one synchronous control exchange and are removed as a pair.**

If a `\obt` user turn appears without a following assistant response, the `\obt` turn is still removed.

No additional signature is required because the synchronous conversation structure already identifies the response associated with the `\obt` request.

---

## 13. Defence in Depth

Pontis becomes the authoritative ingress filter for historical external-client `\obt` exchanges.

Existing defensive filtering already present in Repetere and Moderari remains in place.

It should not be removed as part of the Nuntius migration.

The intended protection is therefore:

```text
Pontis
    -> authoritative control-history sanitation

Repetere / Moderari
    -> existing defensive sanitation
```

This preserves the existing model-context safety boundary with minimal additional work.

---

## 14. Vestigare Boundary

Live control commands are intercepted before model execution:

```text
Client
    |
    v
Pontis
    |
    v
Nuntius
    |
    v
Owner
```

They do not enter the normal Repetere -> Moderari -> model path.

Historical control exchanges returned by an external client are removed by Pontis before normal model execution.

Therefore:

> **`\obt` requests and their associated control responses must not appear in Vestigare conversational Trace.**

The resulting execution condition may still belong in Trace.

Examples include:

```text
selected provider
selected model
effective system prompt
```

The operational command used to establish that state remains control-plane evidence rather than conversational evidence.

# Implementation Roadmap

## N1 — Existing `\obt` Investigation

**Status:** Complete.

Moderari, Repetere and Pontis have been examined.

Confirmed:

- existing consume-or-forward behaviour;
- service-local ownership;
- current session handling;
- current response behaviour;
- control/model separation;
- `\obt rogare start` remains Pontis-owned.

---

## N2 — Common Control Contract

**Status:** Design agreed.

This document defines:

- command taxonomy;
- `/control/obt`;
- request envelope;
- service-token routing;
- reserved `select` semantics;
- Servire registry shape;
- response representation;
- query behaviour;
- listener behaviour;
- external client translation;
- Pontis history sanitation;
- Vestigare boundary.

The contract should now be treated as the implementation baseline for N3 onward.

---

## N3 — Servire Registry

Implement the minimum active control-plane registry.

Required information:

```text
service name
endpoint
obt_enabled
active state
listeners[]
```

Required behaviour:

- expose the active registry to Nuntius;
- allow an empty healthy registry;
- update active service state as services start and stop;
- prevent invalid/duplicate service definitions where relevant.

No command catalogue is required.

---

## N4 — Nuntius Routing Core

Implement:

```text
POST /control/obt
        |
        v
validate envelope
        |
        v
parse service token
        |
        v
detect reserved `select` operation
        |
        v
lookup service in Servire registry
        |
        v
send complete unchanged command envelope
to owner's /control/obt
        |
        v
receive authoritative response
        |
        v
return terminal response to originator
```

Also implement:

- request correlation;
- timeout handling;
- Servire bootstrap;
- in-memory registry;
- registry refresh/update;
- baseline diagnostics.

---

## N5 — Pontis External Interception

Implement the external control boundary.

Flow:

```text
incoming request
      |
      +-- terminal \obt?
      |      |
      |      +-- Pontis-owned?
      |      |       -> execute locally
      |      |
      |      +-- otherwise
      |              -> Nuntius
      |
      +-- ordinary request
             |
             +-- remove historical
             |   \obt user + assistant pairs
             |
             v
          normal model path
```

Pontis must:

- preserve existing session identity;
- generate command `request_id`;
- supply `origin`;
- translate Nuntius response `message` into an OpenAI-compatible assistant response;
- retain ordinary model routing unchanged.

---

## N6 — Repetere Migration

Implement:

```text
POST /control/obt
```

Move existing Replay-owned command handlers behind the explicit control endpoint.

Preserve:

- existing Replay command semantics;
- existing defensive `\obt` filtering;
- relevant Replay-domain diagnostics.

Stop using conversational traversal as the normal mechanism for external Replay commands.

---

## N7 — Moderari Migration

Implement:

```text
POST /control/obt
```

Move existing Moderari-owned commands behind the common endpoint.

Preserve:

- existing command semantics;
- existing defensive history filtering;
- model-context exclusion behaviour.

Add the session-scoped `Pass-through` control capability when required for Replay fidelity.

---

## N8 — `select` Response Distribution

Implement and validate the reserved `select` behaviour.

Example:

```text
\obt praebere select model X
```

Successful flow:

```text
Praebere
    |
    v
Nuntius
    |
    +--> originator
    |
    +--> configured listeners
```

Required behaviour:

- only successful `select` responses are distributed;
- ordinary query responses are not distributed;
- do not duplicate delivery to a listener that is already the originator;
- listener failures are diagnostic and do not overwrite the authoritative owner result.

---

## N9 — Praebere Native Adoption

Implement Praebere control commands directly against the new contract.

Likely initial commands include:

```text
\obt praebere providers
\obt praebere models
\obt praebere select model <model>
```

Praebere becomes the first service to adopt Nuntius natively rather than migrate an inherited conversational command route.

---

## N10 — End-to-End Validation

Validate:

```text
external command
    -> Pontis
    -> Nuntius
    -> correct service
    -> authoritative response
    -> correct originator
    -> listeners only when required
```

Then validate the next normal external-client request:

```text
client history
    |
    v
Pontis sanitation
    |
    v
Repetere
    |
    v
Moderari
    |
    v
model
```

Confirm:

- historical `\obt` request removed;
- associated assistant response removed;
- neither appears in Vestigare conversational Trace;
- resulting execution state is still represented where appropriate;
- `\obt rogare start` remains Pontis-local;
- no command-routing loops exist;
- ordinary ask/answer behaviour remains regression-clean.

# Project Completion

The Nuntius control-plane project is complete when:

1. Servire authoritatively exposes the active service registry.
2. Nuntius maintains that registry.
3. Pontis consumes Pontis-owned commands locally.
4. Other external `\obt` commands are routed to Nuntius.
5. Nuntius routes using the service token after `\obt`.
6. Nuntius recognises the reserved `select` operation.
7. Repetere and Moderari expose `/control/obt`.
8. Praebere uses the common contract.
9. Solicited commands always return one terminal outcome.
10. Successful `select` results reach configured listeners.
11. Ordinary query results return only to their originator.
12. External-client control history is removed by Pontis before model execution.
13. Existing downstream defensive filtering remains.
14. `\obt` control exchanges do not appear in Vestigare conversational Trace.
15. Ordinary Lumen ask/answer execution remains regression-clean.

After this point, development returns to the main M0.1 roadmap with Nuntius treated as completed foundational control-plane infrastructure.
