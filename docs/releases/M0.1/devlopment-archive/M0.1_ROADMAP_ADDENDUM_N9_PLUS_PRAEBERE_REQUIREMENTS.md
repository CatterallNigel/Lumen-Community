# 1. Purpose

N9 is the first deliberate use of the completed Nuntius control plane by a service
that did **not** previously depend on legacy conversational `\obt` traversal.

The purpose is therefore larger than adding three commands to Praebere. N9 must prove
that a Lumen service can adopt the common control-plane contract natively:

```text
originator
    ↓
Pontis / Lumen control origin
    ↓
Nuntius
    ↓
Praebere
    ↓
provider/model operation
    ↓
Nuntius
    ↓
originating caller
    └── configured additional consumers only
```

The implementation must preserve the existing architectural boundary:

> **Moderari decides how the model is used. Praebere ensures the configured model
> provider is available to be used.**

Praebere owns provider/model capability and lifecycle. It must not become a
conversation, prompt, tool, Trace, Replay or assessment service.

# 2. Authoritative N9 Requirements

The M0.1 main roadmap defines Phase 6 as:

- [ ] Finalise `\obt providers`.
- [ ] Finalise `\obt models`.
- [ ] Finalise `\obt model select <model>`.
- [ ] Make Praebere the executor of provider/model operations.
- [ ] Return provider/model query results to the originating caller.
- [ ] Deliver discovery results to Rogare/Moderari where Servire configuration
  requires it.
- [ ] Avoid broadcasting provider/model lists to unrelated services.
- [ ] Verify selected model/provider state is represented correctly in subsequent
  execution evidence.

The Nuntius migration project adds the architectural objective:

- [ ] Praebere adopts the completed common control plane natively.
- [ ] Provider/model query and selection commands use the same Nuntius request and
  response contract already proven by migrated services.
- [ ] No legacy conversational `\obt` transport is introduced merely to support
  Praebere.

**N9 exit condition:** Rogare and external clients use the same Nuntius path for
provider/model discovery and selection, with Praebere as the authoritative executor.

# 3. Architectural Boundaries

## 3.1 Praebere Owns Provider Capability

Praebere owns:

- [ ] provider process lifecycle;
- [ ] provider health and reachability;
- [ ] provider ownership tracking;
- [ ] provider discovery;
- [ ] model discovery;
- [ ] model availability/state;
- [ ] model selection;
- [ ] configured/active provider and model identity;
- [ ] provider-specific lifecycle operations;
- [ ] operational logging and health for those responsibilities.

Praebere does **not** own:

- conversational sessions;
- prompts or responses;
- context management;
- system-prompt policy;
- model behavioural orchestration;
- external tool declaration/execution;
- Trace;
- Replay;
- assessment.

## 3.2 Provider-Specific Knowledge Stays in Praebere

- [ ] Do not add Ollama lifecycle/discovery logic to Moderari.
- [ ] Do not add Ollama lifecycle/discovery logic to Rogare.
- [ ] Do not add Ollama lifecycle/discovery logic to Pontis.
- [ ] Do not add provider-specific start/stop behaviour to Servire.
- [ ] Keep provider implementation details behind Praebere/provider-adapter
  boundaries.
- [ ] Model selection exposed outside Praebere describes Lumen model intent rather
  than requiring callers to understand provider endpoints or provider APIs.

## 3.3 M0.1 Provider Scope

- [ ] Treat **Ollama** as the supported M0.1 model provider.
- [ ] Preserve Ollama's expected local provider endpoint/port (`11434`) unless
  explicitly configured otherwise.
- [ ] Do not claim LM Studio or other provider support as part of M0.1 acceptance.
- [ ] Keep the architecture provider-neutral enough that another provider adapter can
  be added later without changing the Nuntius control contract.

# 4. Native Praebere Control Surface

## 4.1 Standard Control Endpoint

- [ ] Implement Praebere's standard Nuntius-addressable control endpoint.
- [ ] Accept the common Lumen control request envelope.
- [ ] Preserve `request_id`, `session_id`, origin and canonical/raw command metadata.
- [ ] Return common response semantics:
  - `204` — command not handled;
  - `200` without body — successful execution;
  - `200` with body — successful query/request;
  - `4xx/5xx` — recognised command failure.
- [ ] Ensure every solicited request has exactly one terminal outcome.
- [ ] Ensure success is never inferred from silence.
- [ ] Keep detailed control traffic outside conversational Trace.

## 4.2 Command Discovery

Nuntius now supports service-owned command discovery. Praebere must participate
natively rather than requiring Nuntius to know Praebere's command catalogue.

- [ ] Expose Praebere's supported `\obt` commands through its service-owned discovery
  mechanism.
- [ ] Ensure a Nuntius restart/catalogue rebuild can rediscover Praebere commands.
- [ ] Ensure command discovery reflects the commands actually implemented by the
  running Praebere version.
- [ ] Do not duplicate a hard-coded Praebere command list in Nuntius.

# 7. `\obt model select <model>`

## 7.1 Selection Semantics

- [ ] Implement/finalise `\obt model select <model>`.
- [ ] Validate the requested model against Praebere's authoritative cached catalogue;
  model selection must not perform live Ollama discovery.
- [ ] Reject unknown/unavailable models explicitly rather than silently retaining or
  substituting another model.
- [ ] On success, make Praebere authoritative for the selected provider/model state.
- [ ] Return explicit positive acknowledgement containing the effective selection.
- [ ] Preserve the previous valid selection if a requested selection fails.
- [ ] Make repeated selection of the already-selected model safe/idempotent.
- [ ] Permit runtime-global model selection/change only while there are **no active
  execution sessions**.
- [ ] Once the first session performs model execution, lock the selected runtime-global
  model until all active execution sessions have ended.
- [ ] Reject an attempted model change while any active execution session exists and
  return the authoritative model currently in use.
- [ ] Evaluate known reservation and execution-lock conflicts from Praebere state and
  return them without waiting for provider discovery or status calls.

### 7.1.1 Established Versus Active-Execution Sessions

For M0.1, merely connecting a client must **not** lock model selection.

Two session states are relevant to model selection:

**Established session**

- Pontis has assigned the authoritative `session_id`;
- the session exists and may be used for control operations;
- no model interaction has yet occurred for that session;
- model selection remains possible subject to there being no other active execution
  session.

**Active execution session**

- the session has performed its first model interaction;
- its runtime model execution condition has therefore been established;
- the runtime-global selected model is locked while this or any other active execution
  session remains active.

This distinction supports the required research workflow:

```text
client connects
    ↓
Pontis establishes session_id
    ↓
model discovered/selected
    ↓
optional Trace start
    ↓
first model interaction
    ↓
session becomes active execution
    ↓
runtime-global model locked
```

The model becomes selectable again only after all active execution sessions have ended.

### 7.1.2 Preferred Model Versus Selected Model

Praebere must distinguish:

1. **available models** — models actually discovered from Ollama;
2. **preferred model** — an optional installation/UI preference;
3. **selected model** — the authoritative runtime-global model used for execution.

A preferred model is not itself an execution selection.

- [ ] Praebere queries Ollama for available models at startup.
- [ ] Persist or otherwise retain the resulting authoritative catalogue for ordinary
  runtime queries, selection validation and UI presentation.
- [ ] Do not re-query Ollama during ordinary `models`, model-selection or UI-state
  requests. A newly installed or removed model becomes visible through the explicit
  **Refresh Models** operation.
- [ ] A configured preferred model is valid only if it exists in the discovered model
  list.
- [ ] An unavailable preferred model must not prevent Praebere/stack startup.
- [ ] Praebere must remain operational with no selected model.
- [ ] Do not silently substitute another model when the preferred model is unavailable.
- [ ] Do not automatically apply the preferred model to a newly connected external
  client.

## 7.2 Selection Intent Versus Provider Implementation

A caller should be able to select a model without knowing how Praebere implements the
provider operation.

The caller may express:

```text
\obt model select qwen2.5-coder:14b-32k
```

but should not need to express:

```text
provider = ollama
endpoint = 127.0.0.1:11434
load via provider-specific API
```

- [ ] Keep provider endpoint/API knowledge inside Praebere.
- [ ] Do not make Rogare or external clients encode provider implementation details.
- [ ] Keep the Nuntius command/response contract provider-neutral.

# 8. Provider and Model Runtime State

Praebere must continue to distinguish:

1. provider process existence;
2. provider API reachability;
3. model local availability;
4. model residency/readiness;
5. preferred model identity;
6. authoritative runtime-global selected model identity;
7. model-selection lock state.

- [ ] Do not collapse these states into a single `running` flag.
- [ ] Ensure provider/model query responses expose enough state to diagnose a cold or
  unloaded model without implying provider failure.
- [ ] Ensure model selection state survives normal subsequent requests for the
  runtime-global M0.1 scope.
- [ ] Serve ordinary model-state requests from Praebere's cached catalogue and
  authoritative reservation/execution state without live Ollama discovery.
- [ ] Expose whether model selection is currently unlocked or locked by active execution sessions.
- [ ] Re-enable selection only when no active execution sessions remain.
- [ ] Identify cached catalogue state and the last successful discovery refresh so
  callers do not mistake it for continuous live provider discovery.
- [ ] Reconcile provider catalogue reality only at startup, explicit **Refresh
  Models**, or when a real load/unload operation supplies a definitive result.

## 8.1 Activation Failure and Reservation Release

- [ ] On first ask, request model loading through Praebere only when the selected
  model is not already resident.
- [ ] If Ollama reports that the selected model cannot be loaded, do not register the
  requesting session as an active execution session.
- [ ] Cancel only the requesting session's model reservation; preserve reservations
  held by every other open session.
- [ ] Persist the effective selected model, remaining reservation identifiers,
  execution identifiers, selection state and failure outcome through Praebere's
  authoritative state-transition path.
- [ ] Return a controlled activation error to the requesting client that explicitly
  reports both the model-load failure and cancellation of that session's reservation.
- [ ] If no other session retains a reservation, return selection state `available`;
  otherwise retain `reserved` for the remaining sessions.

# 9. Ollama Lifecycle Ownership

Existing Praebere lifecycle behaviour remains an N9 invariant.

- [ ] If Praebere started Ollama, Praebere may stop it during the corresponding
  lifecycle shutdown.
- [ ] If Ollama was already running independently, Praebere must not stop it unless
  configuration explicitly grants that ownership.
- [ ] Servire requests provider lifecycle behaviour through Praebere; Servire must not
  kill/manage Ollama directly.
- [ ] Preserve the existing extended Praebere shutdown allowance in Servire where
  required by real provider shutdown behaviour.
- [ ] Do not hide a provider-shutdown defect by continually increasing Servire
  timeouts.
- [ ] Verify discovery and model selection work both when Praebere starts Ollama and
  when it adopts an already-running Ollama instance.

# 10. Readiness and Idle-Eviction Behaviour

Praebere architecture already distinguishes model availability from readiness. N9
should implement everything currently unblocked while preserving the intended future
request-orchestration boundary.

- [ ] Provide/retain a provider-neutral Praebere operation capable of ensuring the

- [ ] Detect when Ollama remains healthy but the selected model has become non-resident

- [ ] Allow Praebere to reload/warm the selected model without changing the selected

- [ ] Keep the decision to gate an inference request on readiness with Moderari, not

- [ ] Keep the implementation of readiness with Praebere.
- [ ] Do not make completion of broader automatic Moderari readiness gating a blocker

**Future integration boundary:** a later Moderari integration may call Praebere
`ensure-ready` before forwarding inference. That must reuse Praebere's provider-neutral

# 11. Rogare Integration

- [ ] Rogare obtains the available model list through the Nuntius/Praebere control path.
- [ ] Rogare does not query Ollama directly.
- [ ] Display available models in a dropdown associated with session start/stop controls.
- [ ] If an available preferred model is configured and no authoritative model is
  already selected/locked, show the preferred model as the initial Rogare dropdown
  choice.
- [ ] A preferred-model dropdown choice must not be confused with authoritative
  runtime selection; selection becomes authoritative only through the Praebere
  `\obt model select <model>` path.
- [ ] When no active execution sessions exist, allow the researcher to change the
  dropdown selection.
- [ ] Before model execution/session activation, establish the chosen model through
  Praebere and wait for authoritative success.
- [ ] Once any active execution session exists, disable model choice and display the
  authoritative runtime-global model currently in use.
- [ ] If Rogare starts/restarts while another execution session is active, recover the
  authoritative model and show it as locked rather than offering a new choice.
- [ ] Rogare updates visible selected-model state only after authoritative success.
- [ ] Failed selection remains visibly failed and does not imply the requested model
  became active.
- [ ] Existing M0.1 tool-provider behaviour remains separate from model-provider
  selection.

The already-established M0.1 tool boundary remains unchanged:

- [x] external clients own their own tool declaration, execution and result handling;
- [x] Rogare has no native tool environment and uses an external tool provider;
- [x] Pi is the supported M0.1 tool provider for Rogare in its expected/default
  installation location;
- [x] alternative Rogare tool providers are not claimed for M0.1.

# 12. Moderari Integration

Moderari must consume provider/model authority without acquiring provider lifecycle
knowledge.

- [ ] Deliver provider/model discovery results to Moderari only where Servire
  configuration explicitly requires it.
- [ ] Ensure Moderari can obtain the authoritative selected provider/model state needed
  for subsequent model execution.
- [ ] Remove or avoid duplicated provider/model authority in Moderari where the N9
  implementation makes it redundant.
- [ ] Do not move Ollama start/stop/discovery code into Moderari.
- [ ] Ensure changing the selected model affects subsequent new model execution as
  intended.
- [ ] Enforce the M0.1 runtime-global selection scope consistently across concurrent
  sessions.
- [ ] Ensure a model selection made from one session is reflected as the authoritative
  model for subsequent requests from every session.
- [ ] Do not imply that Moderari's session-scoped system-prompt policy makes provider
  or model state session scoped.

**M0.1 decision:** provider and selected-model state are **runtime-global**. Praebere
maintains one authoritative provider/model selection for the local Lumen runtime.

Model selection/change is permitted only while there are no active execution sessions.
An established session that has not yet performed model interaction does not by itself
lock selection. Once the first model interaction occurs, the selected model is locked
until all active execution sessions have ended. New concurrent sessions inherit that
already-established runtime model and cannot change it.

This is deliberately simpler than per-session model selection and prevents one
concurrent researcher from changing another session's model execution condition.
The UI, control responses and execution provenance must make this scope explicit.

**Optional polish / future development:** if N9 is completed with sufficient time and
the change remains bounded, per-session model selection may be investigated. It is not
an N9 or M0.1 blocker and otherwise remains future development.

# 21. N9+ Exit Condition

N9+ is complete when:

1. Praebere is a first-class native Nuntius control-plane participant;
2. `\obt providers`, `\obt models`, and `\obt model select <model>` are authoritative
   Praebere operations;
3. Rogare and external clients use the same control path;
4. results return to the correct originator and only configured additional consumers;
5. provider/model implementation details remain encapsulated by Praebere;
6. selected/effective provider-model state is runtime-global for M0.1, model changes
   are allowed only before active execution begins or after all execution sessions end,
   and that scope/lock state is accurately reflected in UI, control responses and
   subsequent execution evidence;
7. the configured Ollama endpoint is treated as external infrastructure: Praebere
   verifies availability, while Lumen never starts or stops the Ollama process;
8. control traffic remains outside model context and conversational Trace;
9. Nuntius diagnostics provide correlation and terminal outcome evidence;
10. all modified-service tests, Ruff and mypy checks are clean; and
11. the Praebere-owned UI exposes authoritative provider, model availability/residency,
    persistence, reconciliation and execution-lock state and provides the bounded
    safe M0.1 actions without replacing the Nuntius/`\obt` control path; richer
    provider-neutral readiness remains optional post-M0.1 work; and
12. provider/model fidelity work thereby unblocked in Repetere is either completed
    where practical or explicitly carried forward with no ambiguity.

At that point N9 has proved the intended architectural point: a new Lumen capability
can adopt the common control plane directly, without first acquiring a legacy
conversational command path.
