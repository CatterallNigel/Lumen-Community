## 1. Purpose

This addendum groups the work that is specifically owned by, or must be validated while working in, **Moderari**. It allows Nuntius N7 migration and the remaining M0.1 Moderari work to be completed together where practical without changing the ordering or historical structure of the main M0.1 Development Roadmap.

The main roadmap remains authoritative for overall M0.1 scope. This document is a working extraction/checklist for the Moderari service pass.

## 2. N7 — Moderari Migration

**Objective:** Move Moderari-owned external control commands onto the explicit Nuntius control path.

### N7.1 Standard Control Endpoint

- [x] Add the standard Moderari control endpoint used by Nuntius.
- [x] Accept the common Nuntius control envelope, including request/session/origin correlation where supplied.
- [x] Keep the normal model/data execution endpoint separate from the control endpoint.
- [x] Ensure unsupported/unowned commands follow the common control response semantics rather than entering model execution.

### N7.2 Existing Handler Migration

- [x] Identify existing Moderari `\\obt`/backchannel command handlers.
- [x] Adapt Moderari-owned handlers to the common Nuntius response contract.
- [x] Return `200` for successfully handled commands, with a body where the command is a query.
- [x] Return `204` where Moderari legitimately has no response/responsibility under the common contract.
- [x] Return explicit errors for malformed, invalid or failed Moderari-owned operations.
- [x] Preserve request/session correlation on query responses.

### N7.3 Servire / Nuntius Registration

- [x] Add/verify Moderari's `obt_enabled` capability in Servire configuration.
- [x] Register Moderari-owned command tokens/routes in the Servire catalogue.
- [x] Verify Nuntius receives the Moderari route when the service becomes available.
- [x] Verify Nuntius removes/updates that route when Moderari stops or its catalogue state changes.
- [x] Verify Moderari is reachable through Nuntius without broadcasting commands to unrelated services.

### N7.4 Defensive Compatibility

- [x] Retain historical compatibility behaviour as a defensive compatibility path rather than as the authoritative command path.
- [x] Clearly separate defensive compatibility handling from the authoritative Nuntius path.
- [x] Ensure the compatibility path cannot cause duplicate command execution.
- [x] Retain the compatibility path for defensive purposes in M0.1 and mark its eventual retirement as future development.

### N7.5 Trace / Context Safety

- [x] Verify client-originated `\\obt` commands routed to Moderari do not enter ordinary model ask/answer execution.
- [x] Verify historical Moderari control/backchannel traffic cannot leak into model conversational context.
- [x] Verify control commands do not appear as conversational turns in Vestigare Trace.
- [x] Where a control action changes an execution condition, ensure the resulting effective condition remains observable as execution evidence.

**N7 exit condition:** Moderari-owned external commands arrive through Nuntius rather than through ordinary model execution, and historical control traffic cannot contaminate model context or conversational Trace.

**Status 2026-08-30:** N7 command migration is implemented and live validated. Historical/backchannel handling is retained only as a defensive compatibility path, is separated from the authoritative Nuntius route, and is recorded for future retirement rather than M0.1 removal.

## 3. N7+ — Moderari System-Prompt Policy

These are existing M0.1 Moderari requirements that should be addressed while Moderari is already under active development.

### 3.1 Required Policy Modes

- [x] Implement **Pass-through**.
- [x] Preserve **Moderari Default** as the normal/default behaviour.
- [x] Implement **Custom** as an exact researcher-defined system-prompt condition.

### 3.2 Pass-through

- [x] Do not replace or alter a client-supplied system prompt.
- [x] If the client supplies no system prompt, do not create one merely because Pass-through is selected.
- [x] Verify Pass-through leaves client-controlled system context unchanged.
- [x] Keep context compaction/checkpoint behaviour independent of system-prompt Pass-through.

### 3.3 Moderari Default

- [x] Preserve current Moderari default system-prompt behaviour.
- [x] Remove/supersede an incoming client system prompt where required by Default mode.
- [x] Inject the Moderari Default system prompt exactly as intended by the existing normal Lumen path.
- [x] Preserve any existing Default-mode tool-related system-prompt processing until deliberately redesigned.

### 3.4 Custom

- [x] Remove/supersede the incoming client system prompt.
- [x] Inject the researcher-defined Custom prompt.
- [x] Do not add, remove, rewrite, merge, normalise or otherwise augment the selected Custom prompt.
- [x] Do not carry tool instructions/descriptions from the removed client system prompt into Custom.
- [x] Keep tool availability separate from tool instructions contained in the Custom prompt.
- [x] Require any desired tool descriptions/tool-use instructions to be explicitly present in the researcher-defined Custom prompt.
- [x] Verify a Custom prompt without tool instructions is not silently augmented when tools are available.
- [x] Verify a Custom prompt containing researcher-supplied tool instructions does not acquire a second Moderari-generated tool block.

**Policy exit condition:** system-prompt behaviour is explicit, selectable and reproducible; Custom is demonstrably the exact researcher-defined prompt rather than a Moderari-generated or tool-augmented derivative.

## 5. N7+ — Saved Custom System Prompts

### 5.1 Persistence

- [x] Add a dedicated MongoDB collection for Moderari saved system prompts.
- [x] Define a minimal schema containing stable `prompt_id`, human-readable `name`, `content`, `owner_id`, `scope`, `created_at`, and `updated_at`.
- [x] Use a simple/default M0.1 owner identity while retaining `owner_id` for future compatibility.
- [x] Retain an explicit `scope` field without implementing multi-user/organisational policy in M0.1.

### 5.2 Editor / Saved Object / Runtime Separation

- [x] List/select saved prompts.
- [x] Load a selected prompt into the Custom editor as a working copy.
- [x] Ensure editing the working copy does not mutate the saved object or active runtime configuration.
- [x] Implement **Apply** independently of persistence.
- [x] Implement **Save As…** to create a new saved prompt without overwriting the source prompt.
- [x] Implement explicit **Update Saved**.
- [x] Implement explicit **Delete Saved**.
- [x] Ensure Save As…, Update Saved and Delete Saved do not silently alter Moderari's active runtime prompt.
- [x] Ensure Apply does not silently create or update a saved prompt.
- [x] Do not store active runtime state as an `is_active` property of a saved-prompt document.

### 5.3 Deliberate M0.1 Boundary

Do **not** add prompt sharing, organisational prompt libraries, mandatory organisational prompts, permission policy or sophisticated prompt version history in M0.1.

**Saved-prompt exit condition:** researchers can safely reuse and modify controlled system-prompt conditions while saved definitions, editor working copies and Moderari's active runtime configuration remain explicit and independent.

## 6. N7+ — Effective System-Prompt Trace Provenance

Live testing during the preceding N6/Vestigare work established that the effective Moderari Default system prompt is **not currently represented authoritatively enough in Trace for Replay fidelity**. This is therefore active M0.1 work rather than a theoretical validation item.

- [x] Validate baseline/Default, Pass-through and Custom executions against Vestigare Trace.
- [x] Ensure Trace unambiguously identifies the **effective system prompt that actually reached the model**.
- [x] Where Moderari supersedes an incoming client system prompt, preserve the incoming prompt as provenance if available, but distinguish it from the active/effective prompt.
- [x] Ensure a superseded incoming prompt cannot later be mistaken for Replay input.
- [x] If the execution path does not naturally expose the effective prompt to Vestigare, implement the minimum explicit provenance mechanism required.
- [x] Prefer the established control architecture for any explicit notification: Moderari → Nuntius → appropriate consumer, correlated to the model/session execution.
- [x] Ensure any such provenance/control notification remains outside conversational Trace turns.
- [x] Retain the actual applied Custom prompt in Trace regardless of later saved-prompt changes or deletion.

**Trace-provenance exit condition:** the Trace provides authoritative evidence of exactly which system prompt reached the model, while preserving any superseded incoming prompt only as distinguishable provenance.

## 7. N7+ — Replay Pass-through Prerequisite

This work crosses the Moderari/Repetere boundary. The Repetere side remains tracked in the N6+ addendum; this section records the Moderari-owned side that should be implemented/validated while Moderari is open.

- [x] Provide a session-scoped Moderari control command capable of establishing Pass-through through Nuntius. **Live command-path validation completed and integrated Repetere use implemented.**
- [x] Return an authoritative success response after the requested session policy has been established. **Observed through `\\obt moderari prompt pass-through` followed by session-local status confirmation.**
- [x] Ensure failure, invalid state or inability to establish the prerequisite produces an explicit non-success response.
- [x] Ensure Repetere can require that acknowledgement before any Replay model interaction begins.
- [x] Ensure Replay does not silently substitute the current Moderari Default or current saved/Applied Custom prompt for the source Trace's effective prompt.
- [x] Ensure Replay reconstructs exactly one active effective system prompt.
- [x] Ensure a superseded incoming prompt and its Moderari replacement are never both reconstructed as active prompts.

### M0.1 Session-Scoped Moderari Constraint

N7 live validation has deliberately revised the earlier shared-system-prompt assumption. Moderari system-prompt policy is now an explicit **session-scoped execution condition**.

A Replay Pass-through prerequisite must therefore target the Replay session itself. It must not alter another active client session and must not silently alter the default policy inherited by subsequently created sessions.

Provider/model concurrency remains a separate M0.1 question and must not be inferred from this Moderari result.

**Replay/Moderari exit condition:** Repetere can establish and verify Pass-through for its own Replay session through Nuntius without contaminating another session, changing the new-session default, or altering model context outside the targeted Replay session.
