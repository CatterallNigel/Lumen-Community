## D-001 — No Observed `\obt` Control Leakage Between Rogare and Pi

**Area:** N7+ / Moderari / Nuntius / Pontis  
**Status:** Observed — isolation test passed  
**Disposition:** M0.1 evidence; historical defensive-path removal deferred

Testing used Pi and Rogare against the same Lumen stack and underlying Qwen model. The sequence included Pi-first and Rogare-first operation, ordinary conversations, a Rogare `\obt moderari status` request while Pi remained active, and further ordinary client requests.

No Moderari `[Lumen Command]` response or `\obt` control traffic was observed entering Pi's conversational/model context.

### Conclusion

The explicit Nuntius control path behaved as intended during these tests. The retained historical compatibility handling does not need to be removed for M0.1 provided this isolation continues to hold.

Its eventual removal should be combined with future migration of remaining historical backchannel/control traffic to Nuntius.

## D-002 — Moderari `\obt` Introduction Appears Lifecycle-Dependent

**Area:** Moderari / Session Lifecycle  
**Status:** Investigation required  
**Disposition:** Characterise before deciding; no current M0.1 scope change

During the first Pi conversation, Moderari emitted:

```text
[Lumen Moderari v3.2.14.13]

Commands beginning with \obt are handled by Lumen.
They are not sent to the model as prompts.

Use \obt help to list available commands.
```

A later newly started Pi conversation did not display the same introduction. Rogare has also not displayed the introduction in the observed conversation window.

### Working Hypothesis

Moderari may not emit the introduction once per newly created external-client session.

A possible lifecycle is that the introduction is associated with the transition from **zero active sessions to the first active session**, rather than every client-created conversation.

This is not yet proven.

### Planned Controlled Test

1. Close existing Pi and Rogare sessions.
2. Restart Moderari to establish known clean state.
3. Start a Rogare session first.
4. Send one ordinary prompt; do not issue an `\obt` command.
5. Observe whether the Moderari command introduction appears.
6. While Rogare remains active, start Pi.
7. Send one ordinary Pi prompt and observe whether the introduction appears.
8. Close both sessions.
9. Without restarting Moderari, create a new Rogare session.
10. Send an ordinary prompt and observe whether the introduction reappears.
11. If useful, close Rogare and start another Pi session for comparison.

If Rogare never displays the statement while Pi does, investigation should shift toward client/protocol presentation rather than assuming a Moderari lifecycle defect.

### M0.1 Impact

Currently none. The introduction is informational rather than required for successful operation.

## D-003 — Pi and Rogare Produce Materially Different Conversation Behaviour

**Area:** Client Behaviour / Model Context  
**Status:** Reproducible observation; cause not yet proven  
**Disposition:** Aestimare Research Candidate / Future Investigation

Pi and Rogare were used against the same Lumen stack and the same Qwen model.

Rogare generally returned an answer to the current question only.

In Pi, behaviour changed as conversation history accumulated. Qwen began answering previous questions alongside the current question. The observed progression was approximately:

```text
family car -> car answer
new cat -> car + cat
salary -> car + cat + salary
capital of Peru -> car + cat + salary + Peru
```

Rogare did not exhibit this cumulative-answer pattern during the comparable conversation.

### Working Hypothesis

The client is the principal known variable.

Rogare is deliberately a thin conversational client. Pi has its own conversation/runtime behaviour and extensions. The current working hypothesis is therefore that **Pi is constructing, retaining, presenting, or otherwise influencing conversational context differently from Rogare**, causing Qwen periodically to interpret accumulated questions as a set requiring collective answers.

Qwen ultimately generates the responses, so the cause should not be attributed conclusively to Pi until effective model inputs are compared.

### Future Verification

Record equivalent Pi and Rogare conversations through Vestigare and compare the effective requests/context presented downstream.

This should distinguish client/orchestration-induced behaviour, where effective model inputs differ, from model behavioural variation, where materially equivalent inputs produce different behaviour.

## D-004 — Tool Selection Varies Across Comparable Questions and Client Contexts

**Area:** Model Behaviour / Tools / Pi / Rogare  
**Status:** Observed  
**Disposition:** Aestimare Research Candidate; no M0.1 change

Tool-selection behaviour varied across executions using the same underlying Qwen model.

Examples observed:

- Pi answered the London–New York distance directly from model knowledge in one conversation.
- Rogare received a model-generated `web_search` tool call for the London–New York distance.
- Pi answered the capital of Peru directly in one conversation.
- In a later Pi conversation, the capital-of-Peru question caused a `web_search` attempt.

Therefore comparable factual questions did not consistently result in the same decision about whether external evidence was required.

### Research Significance

Two executions can eventually produce the same factual answer while following materially different behavioural paths:

```text
prompt -> parametric knowledge -> answer
```

versus:

```text
prompt -> decision to seek external evidence -> tool request -> tool execution -> answer
```

or:

```text
prompt -> decision to seek external evidence -> tool request -> tool failure -> recovery behaviour
```

This is directly relevant to Aestimare's objective of assessing observable model behaviour rather than merely answer correctness.

## D-005 — Rogare Does Not Execute Pi-Owned `web_search` Tool Calls

**Area:** Rogare / Pi / Tool Runtime  
**Status:** Explained  
**Disposition:** No M0.1 action from this observation

When Qwen requested `web_search` during a Rogare conversation, Rogare received the raw tool-call completion rather than executing Pi's web-search capability.

When Pi generated a `web_search` request, Pi's `@ollama/pi-web-search` extension attempted execution. That attempt failed because Ollama required authentication and initiated an `ollama signin` browser flow.

### Conclusion

The distinction is not simply that Rogare cannot open an authentication browser.

Pi owns/provides the relevant web-search tool runtime. Rogare does not implement Pi's `web_search` extension and therefore has no corresponding tool implementation to execute that model-generated request.

This is consistent with different clients exposing different runtime capabilities despite using the same underlying model.

## D-006 — Client Tool Availability Is Part of Effective Model Behaviour

**Area:** Architecture / Behavioural Evidence  
**Status:** Observation derived from integration testing  
**Disposition:** Aestimare Research Candidate / Future Architecture Consideration

The tests demonstrate that specifying only the model is insufficient to characterise an execution.

Effective behaviour can depend on at least:

- model;
- client;
- exposed tool definitions;
- tool runtime availability;
- authentication state;
- accumulated conversation context;
- Lumen orchestration/session state.

For future behavioural assessment, provenance should preserve enough information to distinguish these execution conditions.

A result such as `Lima` may appear identical at the answer level while arising from substantially different execution paths and evidence conditions.

## Current M0.1 Position

None of these discoveries currently justify expanding M0.1 scope.

The important N7/N7+ result is that no `\obt` control leakage was observed across the tested Pi/Rogare interaction paths.

The Moderari introduction lifecycle should be characterised because the test is inexpensive and may reveal useful session-state behaviour. Unless it exposes a material usability or correctness problem, resulting engineering work should remain outside M0.1.

The Pi/Rogare context and tool-selection differences should be preserved as future research evidence rather than treated as release blockers.
