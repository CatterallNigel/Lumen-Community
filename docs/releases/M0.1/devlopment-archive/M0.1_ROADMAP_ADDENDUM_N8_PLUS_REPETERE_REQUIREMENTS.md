## 1. Purpose

N1 through N7 of the Nuntius control-plane migration are complete. The next active
development phase is **N8 — Nuntius Diagnostics and UI**.

This addendum defines the work to be performed while Nuntius and Servire are already
open for modification, and carries forward the remaining Repetere requirements that
must not be lost as the main M0.1 roadmap advances.

It does **not** replace or reorder the main M0.1 roadmap. The parent roadmap remains
the release-level source of truth.

The working principle remains:

> When a roadmap dependency makes a service ready for modification, complete all
> currently unblocked M0.1 work owned by that service before leaving it. Requirements
> that depend on unfinished work in another service remain explicitly identified.

For this pass the normal implementation boundary is:

- **Nuntius** — primary N8 implementation;
- **Servire** — Nuntius operational surface plus adjacent UI/configuration/lifecycle remediation;
- **Fiducia** — only where required to correct the already identified Servire-managed
  shutdown/log-cleanup defects;
- **Repetere** — requirements carried forward and reconciled, but not automatically
  pulled into the N8 implementation pass unless directly unblocked by Nuntius/Servire work.

Praebere remains the next native Nuntius adopter after N8.

# 2. Current Baseline

The following control-plane work is already established and is not to be reimplemented
during N8:

- [x] Nuntius bootstraps from the Servire-defined active service catalogue.
- [x] Nuntius maintains the active routing dictionary.
- [x] Runtime service start/stop updates are reflected in Nuntius.
- [x] Nuntius logs the number of currently available services on startup/restart.
- [x] Common `\obt` request/response semantics are implemented.
- [x] Pontis routes external non-Pontis-owned `\obt` requests to Nuntius.
- [x] Repetere-owned control commands use the explicit Nuntius path.
- [x] Moderari-owned control commands use the explicit Nuntius path.
- [x] Request/session correlation is preserved for migrated paths.
- [x] Detailed Nuntius control-plane traffic remains outside conversational Trace.
- [x] Nuntius diagnostic logging exists for routing, exchanged control messages,
  responses, failures and timeouts.
- [x] Moderari system-prompt policy is session scoped and exposed through Servire.
- [x] Concurrent-session validation has demonstrated independent Moderari policy state.
- [x] Defensive historical command filtering/compatibility remains intentionally retained;
  eventual retirement is future development rather than an N8 requirement.

N8 therefore concentrates on making the existing Nuntius control-plane state
**diagnosable and operationally visible**, rather than redesigning routing.

# 3. N8 — Nuntius Diagnostics and UI

## 3.1 Diagnostic Data Model

Nuntius must expose sufficient bounded operational state to diagnose control-plane
routing without requiring detailed traffic to be copied into Servire's normal
Operational Log.

Implement or confirm structured diagnostic records containing, where applicable:

- [x] request ID;
- [x] originating service/client;
- [x] originating session ID;
- [x] canonical/raw command identity as appropriate;
- [x] resolved target/owner;
- [x] request start time;
- [x] terminal completion time;
- [x] elapsed time;
- [x] terminal HTTP/control result;
- [x] whether a response body was returned;
- [x] timeout/unconfirmed outcome;
- [x] late response after timeout where observable;
- [x] routing failure;
- [x] configuration/catalogue failure;
- [x] delivery failure to the originating/requested response target;
- [x] concise failure reason suitable for diagnostics.

The diagnostic representation is operational evidence, not conversational evidence.
## 3.2 Nuntius Health and Topology State

Expose sufficient current state for Servire to show:

- [x] Nuntius health;
- [x] Servire connectivity;
- [x] catalogue/bootstrap state;
- [x] number of currently available Nuntius-addressable services;
- [x] active route count;
- [x] in-flight request count;
- [x] most recent catalogue refresh/update time where useful;
- [x] current timeout configuration where useful for diagnosis;
- [x] routing/configuration error state where present.

The UI should make it possible to distinguish:

- healthy Nuntius with zero routes;
- healthy Nuntius with active routes;
- loss of Servire connectivity;
- invalid/incomplete routing configuration;
- command execution failure at the destination service.
## 3.3 Bounded Recent Request History

- [x] Maintain a bounded recent diagnostic history rather than an unbounded in-memory log.
- [x] Define the history bound explicitly in configuration or as a documented constant.
- [x] Preserve enough completed request history to investigate recent routing failures.
- [x] Do not make diagnostic history part of Vestigare conversational Trace.
- [x] Do not duplicate the full diagnostic history into Servire's normal Operational Log.
- [x] Ensure diagnostic-history failure cannot prevent normal Nuntius routing.
## 3.4 Nuntius Diagnostics API

Provide a read-only operational interface suitable for Servire.

At minimum Servire must be able to retrieve:

- [x] current health/connectivity summary;
- [x] active route/topology summary;
- [x] in-flight request summary;
- [x] bounded recent request history;
- [x] individual request detail where the UI requires it.

The API must remain domain agnostic. Nuntius should report routing/control facts, not
interpret Replay, prompt, provider or model semantics.
## 3.5 Servire Nuntius Tab

Add **Nuntius** as a first-class Servire service tab.

The Nuntius view should provide a concise operational surface rather than simply
rendering the raw Nuntius log.

Suggested structure:

### Overview

- [x] health;
- [x] Servire connectivity;
- [x] available service count;
- [x] active route count;
- [x] in-flight request count;
- [x] recent failure/error indicator.

### Active Routes / Catalogue

- [x] service;
- [x] endpoint;
- [x] `obt_enabled` state;
- [x] owned command/service routing information appropriate to the current contract;
- [x] response targets where operationally useful.

### Recent Requests

- [x] request ID;
- [x] origin/session;
- [x] resolved owner;
- [x] result;
- [x] elapsed time;
- [x] timestamp;
- [x] clear timeout/failure/late-response indication.

### Request Detail

- [x] enough correlated information to reconstruct the control-plane lifecycle;
- [x] no unnecessary conversational content;
- [x] no model ask/answer content merely for convenience.

The Nuntius tab is the authoritative Servire location for detailed Nuntius
control-plane diagnostics.
## 3.6 Existing Trace-State Synchronisation Defect

The main roadmap records a known integration defect in which Rogare's one-time
`\obt vestigare trace status` synchronisation can receive `404` from Nuntius even
though pushed Vestigare → Nuntius → Rogare Trace-state events operate correctly.

- [x] Reproduce the current behaviour.
- [x] Confirm the intended command owner and catalogue registration.
- [x] Correct the route/registration rather than adding a special-case bypass.
- [x] Verify Rogare can reconnect/restart while a Trace is active and recover the
  authoritative Trace state.
- [x] Verify the query remains outside conversational model execution.
- [x] Add regression coverage.

# 4. N8+ — Servire Remediation While the UI Is Open

These items are not a redesign of Servire. They are bounded remediation and
housekeeping tasks that are economical to complete while Servire is already being
modified for the Nuntius UI.

## 4.1 Service Tab Ordering

The current tab order reflects historical implementation order and becomes less
usable as additional services are added.

Change the ordering rule to:

> **Servire first, followed by all other service tabs alphabetically.**

With the current N8 set this should produce:

`Servire → Fiducia → Moderari → Nuntius → Pontis → Repetere → Rogare → Vestigare`

When Praebere is subsequently added it should naturally appear between Pontis and
Repetere.

Requirements:

- [x] Servire remains the first tab.
- [x] All non-Servire tabs are alphabetically ordered by service name.
- [x] Ordering is derived consistently rather than manually maintained in multiple places.
- [x] Existing tab selection/navigation behaviour remains unchanged.
- [x] Add UI/unit regression coverage where practical.
## 4.2 Moderari Tab Navigation Cleanup

The Moderari session UI now contains its own session-scoped navigation and selected
scope. The older outer-level:

`Sessions | Operations | Checkpoints`

navigation is redundant and can be confusing because similar concepts are already
represented inside the Moderari service view.

- [x] Remove the redundant outer Moderari `Sessions / Operations / Checkpoints` level.
- [x] Retain the current Moderari session list and selected-scope UI.
- [x] Retain the selected-session inner navigation:
  `Operations | Checkpoints / Results | System Prompt Policy`.
- [x] Preserve the `Defaults for new sessions` system-prompt-policy scope.
- [x] Verify no functionality becomes inaccessible after removal.
- [x] Verify direct/open-service navigation still behaves correctly.
## 4.3 `config.yml` → `config.yaml`

Standardise the Servire configuration filename.

- [x] Rename the canonical configuration file from `config.yml` to `config.yaml`.
- [x] Update default configuration-path resolution.
- [x] Update source references.
- [x] Update tests and fixtures.
- [x] Update packaging/distribution references.
- [x] Update scripts/commands where applicable.
- [x] Update documentation examples and references.
- [x] Search the repository for stale `config.yml` references before completion.
- [x] Do not retain two competing canonical filenames unless an explicit compatibility
  requirement is discovered.
## 4.4 Validation State Must Not Survive Stack Stop

Servire currently continues to display the previous successful validation result after
all managed services have been stopped. This is misleading because a stopped stack
must be validated again before the next start.

Required behaviour:

- [x] When the stack transitions to the fully stopped state, clear/invalidate the
  previous validation result.
- [x] Do not continue displaying a stale green `Validation passed: ...` message while
  the stack is stopped.
- [x] Preserve validation details only if there is a deliberate historical/audit view;
  do not present them as current validity.
- [x] Require the normal fresh validation before the next stack start.
- [x] Verify Stop All, individual shutdown-to-zero, restart and failed-stop paths.
- [x] Add regression coverage for validation-state transitions.
## 4.5 Fiducia PID Lifecycle Defect

A recurring managed-lifecycle defect remains: stopping the complete stack can leave
Fiducia's PID file behind, and subsequent managed startup can fail because the stale
PID is treated as evidence of a running Fiducia process.

Investigate the Servire/Fiducia lifecycle boundary, particularly shutdown ordering,
process termination and PID cleanup.

Requirements:

- [x] Reproduce the stale PID after Servire Stop All.
- [x] Establish whether Fiducia exits before or after Servire considers it stopped.
- [x] Inspect shutdown timeout/race behaviour.
- [x] Ensure normal Fiducia shutdown removes its PID file.
- [x] On startup, if a PID file exists, verify that the recorded PID belongs to a live
  Fiducia process before refusing startup.
- [x] Treat a non-live recorded PID as stale, remove/replace the stale file, log the
  recovery and continue startup.
- [x] A genuinely running Fiducia instance must still prevent duplicate startup.
- [x] Verify repeated Start All → Stop All → Start All cycles without manual PID deletion.
- [ ] Ensure PID/runtime files are treated as runtime state for eventual container
  packaging rather than durable application data. **Carried forward to Docker/distribution packaging.**
- [x] Add regression coverage.

## 4.6 Fiducia Clear Logs Defect

Servire's **Clear Logs** action currently fails for Fiducia because the command name
used at the lifecycle boundary does not match the Fiducia CLI command.

The currently identified mismatch is around `clear-logs` / `clear_log` naming and must
be confirmed from the implementation before changing it.

Requirements:

- [x] Confirm the exact command exposed by Fiducia.
- [x] Confirm the exact command Servire invokes.
- [x] Select one canonical lifecycle/log-cleanup command representation.
- [x] Correct the Servire/Fiducia boundary rather than adding UI-specific special casing.
- [x] Verify Clear Logs succeeds when Fiducia is stopped.
- [x] Verify the expected behaviour when Fiducia is running.
- [x] Verify Stack Clear Logs correctly includes Fiducia.
- [x] Verify a Fiducia failure is surfaced accurately without preventing diagnosis of
  other services.
- [x] Add regression coverage.

# 5. Repetere Requirements Carried Forward

The earlier N6+ addendum identified both completed migration work and requirements that
were blocked by Moderari/Vestigare/Nuntius dependencies. N7+ and the subsequent
multi-session work have removed several of those dependencies.

This section is the active carry-forward checklist. It avoids treating the completed
N6 control-plane migration as unfinished Repetere work.

## 5.1 Completed N6 Control-Plane Migration

- [x] Standard Repetere control endpoint exists.
- [x] Repetere-owned `\obt` commands are consumed through the explicit control path.
- [x] Authoritative results return through Nuntius to the originating session.
- [x] Request/session correlation is preserved.
- [x] Repetere control traffic remains outside normal model ask/answer execution.
- [x] Ordinary Repetere proxy/model behaviour remains available.
- [x] Live `\obt repetere list` routing has been exercised through Pontis/Nuntius.
- [x] Defensive compatibility behaviour is retained intentionally for now.

## 5.2 Replay Session Isolation

Every Replay execution must be transactionally isolated.

- [ ] Require every Replay execution to create a new isolated Replay session.
- [ ] Initialise the Replay session only from the source Trace and explicitly defined
  experimental conditions.
- [ ] Ensure sequential Replay runs do not inherit conversational context or temporary
  state from a preceding Replay.
- [ ] Ensure every future Experiment run receives its own Replay session.
- [ ] Verify concurrent Replay sessions remain isolated when that acceptance test becomes
  available.
- [ ] Add regression coverage proving sequential Replay isolation.

## 5.3 Effective System-Prompt Replay

The source Trace's **effective** system prompt is the replay condition that matters.

- [ ] Confirm the authoritative effective-system-prompt representation available to
  Repetere from the source Trace.
- [ ] Confirm Replay cannot reconstruct two simultaneously active system prompts.
- [ ] Replay the effective system prompt captured in the source Trace.
- [ ] Never substitute the current Moderari Default prompt for the source Trace's
  effective prompt.
- [ ] Never substitute the current saved/applied Moderari Custom prompt for the source
  Trace's effective prompt.
- [ ] Reconstruct exactly one active effective system prompt.
- [ ] Retain superseded/incoming prompt material as provenance where available without
  making it an additional active Replay system prompt.
- [ ] Add a system-prompt-sensitive behavioural acceptance capable of exposing duplicate
  or incorrect system context.
- [ ] Verify the effective system prompt appears correctly in the new Replay Vestigare Trace.

## 5.4 Moderari Pass-through Coordination

Moderari's session-scoped Pass-through capability now exists, so this earlier N6+
dependency is no longer conceptually blocked.

For every new Replay session:

- [ ] Repetere issues the Moderari Pass-through override through Nuntius before model
  interaction begins.
- [ ] Preserve Replay session/request identity in the control exchange.
- [ ] Require authoritative positive acknowledgement before Replay model interaction.
- [ ] Treat failure to establish Pass-through as `FAILED / INCOMPLETE`; do not silently
  continue.
- [ ] Abort before recorded model interaction on `204`, `4xx`, `5xx`, timeout or
  unreachable prerequisite state.
- [ ] Retain the prerequisite failure reason as Replay/Experiment evidence.
- [ ] Verify Replay cannot begin under an unintended current Default/Custom condition
  when Pass-through has not been acknowledged.

## 5.5 Provider / Model Replay Behaviour

Do not silently assume whether source provider/model identity is descriptive provenance
or a Replay binding.

- [ ] Determine whether Repetere reads or acts on provider/model identity from the source Trace.
- [ ] Determine whether provider/model identity appears indirectly in reconstructed
  conversational messages.
- [ ] Test whether the same source Trace can be replayed against a different selected
  provider/model without otherwise altering recorded conversational context.
- [ ] Inspect exactly what is sent to the alternate model.
- [ ] Inspect what the resulting Vestigare Trace records.
- [ ] Establish explicitly whether provider/model identity is provenance,
  Replay-binding information, or both.
- [ ] Establish the remaining concurrent provider/model selection constraints.
- [ ] Leave no unsupported provider/model binding/substitution guarantee implicit for M0.1.

## 5.6 Experiment / Run Integration Preparation

These items remain dependent on the later Experiment/Fiducia implementation and should
not cause Repetere to invent a parallel Experiment mechanism.

- [ ] Associate replay-created Traces with Experiment runs when Experiment is introduced.
- [ ] Surface run state as `MATCHED`, `DIVERGED`, or `FAILED / INCOMPLETE`.
- [ ] Surface the first divergence point where available.
- [ ] Preserve the distinction between Repetere divergence detection and future
  Aestimare behavioural assessment.
- [ ] Ensure the Replay session-isolation design is ready for Fiducia-coordinated
  repeated execution.

# 8. N8+ Exit Condition

N8+ may be considered complete when:

1. Nuntius exposes useful bounded health, topology and request-lifecycle diagnostics;
2. those diagnostics are available through a first-class Nuntius view in Servire;
3. a recent control request can be correlated from origin/session/request ID through
   resolved owner to terminal result or failure;
4. routing failures, timeouts and configuration faults can be diagnosed without
   polluting Vestigare conversational Trace or the normal Servire Operational Log;
5. Rogare can recover authoritative active Trace state through the corrected
   `\obt vestigare trace status` route;
6. Servire service tabs use the agreed ordering and the redundant Moderari outer
   navigation has been removed;
7. Servire uses `config.yaml` as its canonical configuration filename;
8. stale validation success is cleared when the stack is stopped;
9. Stop All does not leave a stale Fiducia PID that blocks the next startup;
10. Fiducia participates correctly in Servire Clear Logs;
11. modified-service tests, Ruff and mypy are clean; and
12. the outstanding Repetere requirements in this document remain explicitly tracked
    for their appropriate later implementation/acceptance phase.
