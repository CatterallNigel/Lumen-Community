# M0.1 Trace Model Recording and Replay Requirements

**Status:** Required M0.1 prerequisite for Phase 9 — Experiment Structure  
**Last reconciled:** 2026-09-06

## Revision History

| Version | Date | Change |
|---|---|---|
| 1.0 | 2026-09-05 | Recorded the Trace model-provenance and Replay model-enforcement requirements. |

## 1. Purpose and Scope

This document defines the M0.1 requirements for:

- recording the authoritative provider/model used to create a Vestigare Trace;
- associating that source Trace with an Experiment;
- enforcing the recorded provider/model when Repetere starts each Experiment run;
- associating each Replay-created child Trace with its Experiment and run; and
- reporting deterministic Fiducia outcomes when a scheduled run cannot reproduce the
  recorded execution conditions.

M0.1 retains one runtime-global selected model. It does not add Replay-private model
residency, silent model substitution or general per-session multi-model execution.
Those capabilities remain deferred until sessions can select and own independent
models.

## 2. Service Ownership

| Service | Authority |
|---|---|
| Vestigare | Trace evidence, recording metadata and source/child Trace relationships |
| Repetere | Experiment definition, individual Replay runs, Replay execution and divergence detection |
| Fiducia | Repeated/scheduled run coordination and scheduling outcomes |
| Pontis | Session identity and lifecycle |
| Praebere | Provider state, cached model discovery, model selection, reservation, activation, residency and release |
| Moderari | Session-scoped orchestration and effective system-prompt policy |

Repetere and Fiducia must use the normal Pontis/Praebere lifecycle. Neither may query
or load Ollama directly.

## 3. Vestigare Recording Requirement

Every completed source recording must contain the authoritative model used to create
the Trace:

```json
{
  "model": {
    "provider": "ollama",
    "name": "qwen2.5-coder:14b-32k"
  }
}
```

The identity must come from the authoritative Lumen execution path, not merely from an
unverified client field. Provider and exact model name are required. An immutable
provider digest may also be retained when available without provider-specific coupling.

Recording-level metadata is required even if the model also appears in individual
messages. Repetere and Fiducia must not infer the execution model by decoding message
bodies, consulting Moderari defaults, inspecting resident Ollama models or using the
model selected by another session.

## 4. Experiment and Run Relationships

The Phase 9 relationship is:

```text
Experiment
  -> source Trace
  -> Run 1
       -> fresh Pontis Replay session
       -> Replay-created child Trace
  -> Run 2
       -> fresh Pontis Replay session
       -> Replay-created child Trace
```

At minimum:

- an Experiment references exactly one source Trace for M0.1;
- every run has a stable `run_id` and references its `experiment_id`;
- every run receives a fresh Pontis Replay `session_id`;
- every Replay-created Trace references both `experiment_id` and `run_id`;
- the Experiment retains all prior runs and their evidence; and
- retrying a failed run creates another run rather than mutating the failed record.

The recorded model belongs to the source execution condition and is copied or
referenced as the required model for each run. The run must also record the effective
provider/model actually confirmed for execution.

## 5. Repetere Replay-Start Behaviour

The compatibility check occurs at actual run start. A check performed when an
Experiment is created or scheduled is insufficient because runtime-global state may
change before execution.

Before starting Vestigare recording or model execution, Repetere must:

1. Load the authoritative source recording for the Experiment.
2. Read its provider and model identity.
3. Create a new run and fresh Pontis Replay session identity.
4. Confirm that the recorded model exists in Praebere's cached model catalogue.
5. Obtain the effective global selection, reservation and execution-lock state.
6. Apply the decision rules below.
7. Reserve the required model for the new Replay session through Praebere.
8. Establish the Moderari Replay prerequisite and acquire Vestigare recording.
9. Begin Replay execution; Praebere performs lazy model activation on first execution.

N9.6.4 provider-neutral readiness is not an M0.1 dependency. M0.1 uses completed
N9.6.3 semantics: cached discovery and authoritative selection/reservation followed by
provider reality at activation time.

### 5.1 Decision Rules

| Runtime condition | Required M0.1 result |
|---|---|
| No model is selected and the recorded model is available | Select and reserve the recorded model for the Replay session, then continue. |
| The selected model exactly matches the recorded model | Reserve that model for the Replay session, then continue. |
| A different model is selected, reserved or locked | Record and display a controlled model-conflict failure; do not start recording or model execution. |
| The recorded model is absent from Praebere's cached catalogue | Record and display a controlled model-unavailable failure; do not execute. |
| Recording-level model provenance is missing | Record and display a controlled missing-provenance failure; do not execute. |
| Selection or reservation fails | Preserve the authoritative reason as `FAILED / INCOMPLETE`; do not execute. |
| Lazy model activation fails | Apply Praebere's controlled activation failure, cancel the Replay session's failed reservation, do not register active execution and record the failed run. |
| Vestigare recording cannot be acquired | Record `FAILED / INCOMPLETE`; do not execute unrecorded. |

M0.1 does not offer an override to run with a different active model. A conflict error
must identify both the required and selected models and leave existing selection,
reservations, sessions and residency unchanged.

## 6. Run Result and Cleanup

Each run must terminate as one of:

- `MATCHED` — execution completed and matched the source evidence;
- `DIVERGED` — execution completed and Repetere detected a behavioural difference;
- `FAILED / INCOMPLETE` — prerequisites or infrastructure prevented a complete
  comparable execution.

Every terminal path must close/deactivate the Replay session and release only its own
reservation contribution. Cleanup must be idempotent. Existing sessions and their
reservations must remain unchanged.

Control traffic used for model compatibility, session establishment, prompt policy or
recording coordination remains outside model context and conversational Trace content.

## 7. Fiducia Repeated and Scheduled Runs

Fiducia coordinates repeated runs against an Experiment; it does not own Replay model
logic. At each trigger it asks Repetere to create a fresh run and receives both
asynchronous acceptance and the authoritative terminal result.

The same fail-fast rules apply at scheduled execution time:

- no selection plus recorded model available: select/reserve and proceed;
- selected model matches: reserve and proceed;
- different selected model: fail without substitution;
- missing provenance, unavailable model, selection/reservation failure, activation
  failure or recording contention: record `FAILED / INCOMPLETE`.

Fiducia must retain the trigger, `experiment_id`, `run_id`, Replay session, required
model, effective model where available, failure reason and terminal result. Acceptance
by Repetere is not success.

## 8. Deferred Behaviour

The following remain outside M0.1:

- concurrent execution using different models;
- Replay-private model residency;
- temporarily replacing the global model for Replay;
- substituting another model while calling the run a faithful Replay;
- queued or indefinite waiting for a conflicting model/recording boundary; and
- general per-session model ownership and multi-model lifecycle management.

## 9. Minimum Validation

1. A source recording contains authoritative provider and exact model name.
2. An Experiment references its source Trace.
3. Every run receives a unique `run_id`, fresh Pontis session and child Trace.
4. The child Trace references its Experiment and run.
5. Repetere selects/reserves the recorded model when none is selected.
6. Repetere proceeds when the selected model exactly matches.
7. A different selected/reserved/locked model fails without changing runtime state.
8. Missing provenance and a model absent from cached discovery fail before execution.
9. Activation failure cancels the Replay reservation and creates no active execution.
10. Recording contention fails rather than allowing unrecorded execution.
11. Fiducia records the authoritative terminal result, not request acceptance.
12. Retrying creates a fresh run/session/Trace and preserves failed-run evidence.
13. Same-model multi-session reservation and release remain unchanged.

## 10. Exit Condition

The model-provenance prerequisite is complete when a Phase 9 Experiment can execute
repeated runs using the source Trace's authoritative model condition, reject any
unfaithful or unavailable condition before execution, and preserve one independently
correlated evidence chain for every run.
