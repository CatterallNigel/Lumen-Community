# Lumen Repetere Replay — Stage One: Pontis-Owned Session Preparation

**Status:** Agreed implementation specification  
**Scope:** First implementation stage for the definitive matched and divergent Replay behaviour  
**Agreed:** 9 September 2026

## 1. Objective

Stage One establishes a complete, Pontis-owned Replay execution session before Repetere starts any private replay traffic.

The stage combines the session contract, Pontis session creation and the transfer of model-lifecycle ownership from Repetere to Pontis. These changes must be implemented and tested together because none represents a meaningful operational state by itself.

At the end of successful preparation:

- Pontis has assigned and owns one Repetere session.
- Pontis has created and bound an empty ACP tool-provider session.
- Praebere has selected, reserved, loaded and activated the recorded model for the Pontis session.
- Repetere knows only its Pontis-assigned session ID and that the session is active.
- No conversation, user ask, system prompt or Trace message has been generated by preparation.
- Repetere can start Vestigare and begin its existing private Replay process.

## 2. Ownership rules

### Repetere

Repetere owns the Experiment and Run. It:

- Determines the model required by the recorded source Trace.
- Starts the Run in `PREPARING` state.
- Requests a prepared Replay session from Pontis.
- Stores the session ID returned by Pontis.
- Starts Vestigare only after Pontis reports the session `ACTIVE`.
- Begins private replay comparison only after Vestigare starts successfully.

Repetere does not:

- Create, propose or format a Lumen session ID.
- Create an ACP session.
- Send working-directory or session-bootstrap metadata.
- Send a canned prompt or conversational ask during preparation.
- Select, reserve, activate, release or unload the model directly through Praebere.

### Pontis

Pontis is the sole session authority. It:

- Generates the session ID using its existing origin-based convention.
- Creates the authoritative empty Lumen session with origin `repetere`.
- Selects and reserves the requested model through Praebere.
- Creates and binds the empty ACP tool-provider session.
- Activates the model through Praebere.
- Reports preparation progress and the terminal preparation result to Repetere.
- Owns rollback if any preparation operation fails.
- Owns later closure of the session and its internal ACP resources.
- Informs Praebere when the session terminates.

### Praebere

Praebere remains authoritative for the model lifecycle. It:

- Validates model availability.
- Selects and reserves the requested model for the Pontis-assigned session.
- Loads and activates the model.
- Rejects conflicts or unavailable models.
- Cancels or releases the requesting session's reservation after failure or termination.
- Unloads the model only when no other session requires it.

### Nuntius

Nuntius transports the control requests and responses. It:

- Preserves the request origin `repetere`.
- Preserves the Pontis-assigned session ID on downstream Praebere operations.
- Uses the configured long model-lifecycle timeout for operations that can load or unload a model.

## 3. Repetere-to-Pontis start contract

Repetere sends one composite control request through Nuntius:

```text
\obt pontis session start model <recorded_model> activate
```

Example:

```text
\obt pontis session start model qwen2.5-coder:14b-32k activate
```

The control envelope supplies:

```text
origin: repetere
```

The command supplies:

- The exact model recorded in the source Trace.
- The instruction to prepare an active execution session.

Repetere supplies no session ID. Pontis assigns it.

Repetere supplies no working directory, conversation history, system prompt, user ask or other bootstrap metadata. The prepared session is empty.

## 4. Successful preparation sequence

1. The operator starts a staged Replay.
2. Repetere creates the Run and records:

   ```text
   PREPARING
   ```

3. Repetere reads the exact required model from the source Trace metadata.
4. Repetere sends the composite Pontis start command through Nuntius.
5. Pontis validates that the request origin is `repetere` and that a model was supplied.
6. Pontis generates the authoritative session ID using its existing convention, for example:

   ```text
   session-repetere-...
   ```

7. Pontis creates an empty authoritative Lumen session with origin `repetere`.
8. Pontis sends Praebere, using the Pontis-assigned session ID:

   ```text
   \obt praebere model select <recorded_model>
   ```

9. Praebere validates the model and reserves it for that session.
10. Pontis requires positive acknowledgement that:
    - the requested model was selected;
    - the Pontis session owns a reservation;
    - no incompatible reservation prevents the operation.
11. Pontis creates and binds the empty ACP tool-provider session to its Lumen session.
12. Pontis sends Praebere, using the same Pontis-assigned session ID:

    ```text
    \obt praebere execution activate
    ```

13. Praebere loads the model if necessary and activates execution for the session.
14. Pontis requires positive acknowledgement that model execution is active.
15. Pontis marks its session `ACTIVE`.
16. Pontis returns the active preparation result to Repetere.
17. Repetere stores the returned Pontis session ID against the Run.
18. Repetere starts the child Vestigare Trace using that session ID.
19. After Vestigare confirms recording, Repetere changes the Run to:

    ```text
    RUNNING_COMPARISON
    ```

20. Repetere sends the first recorded Trace request privately to Moderari and begins the existing comparison process.

## 5. Successful response

The response must expose only information that Repetere owns or needs:

```json
{
  "status": "active",
  "session_id": "session-repetere-...",
  "model": "qwen2.5-coder:14b-32k"
}
```

The response must not expose internal ACP identifiers or tool-provider bookkeeping to Repetere.

## 6. Preparation progress

Pontis may issue session-scoped progress updates during a long preparation:

```text
CREATING_SESSION
SELECTING_MODEL
CONNECTING_TOOL_PROVIDER
ACTIVATING_MODEL
LOADING_MODEL
ACTIVE
```

These are preparation progress states, not separate commands and not terminal Run outcomes.

Before Pontis assigns the session ID, the original Nuntius request ID provides correlation. After assignment, progress updates include the Pontis session ID.

Repetere may persist the current preparation phase so its UI can accurately show why the Run has not begun comparing.

## 7. Timeouts

Model loading can legitimately take several minutes. The timeout must therefore be valid across the complete nested request chain.

### Nuntius

Nuntius uses its existing long lifecycle timeout:

```yaml
control:
  model_lifecycle_timeout_seconds: 300.0
```

This timeout applies to Praebere activation and release operations that can synchronously load or unload a model.

### Repetere

Repetere requires its own configurable outer preparation timeout. It must be longer than the Nuntius lifecycle timeout so Repetere does not abandon the request while Pontis, Nuntius and Praebere are still working.

Recommended initial configuration:

```yaml
replay:
  session_preparation_timeout_seconds: 330.0
```

The precise configuration location should follow Repetere's existing configuration structure.

## 8. Preparation failures and rollback

Preparation must terminate if any of the following occurs:

- The recorded model is absent from the source Trace metadata.
- The requested model is unavailable.
- Praebere rejects model selection.
- Another session holds an incompatible model reservation.
- ACP tool-provider session creation or binding fails.
- Praebere rejects execution activation.
- The model fails to load.
- Any preparation operation exceeds its timeout.
- Pontis receives an invalid or incomplete acknowledgement from a dependency.

Pontis owns rollback because Pontis owns the session and knows which resources were created.

The rollback sequence is:

1. Stop any preparation work still in progress.
2. Close any ACP tool-provider resources that were created.
3. End the authoritative Pontis session.
4. Inform Praebere that the session terminated.
5. Praebere cancels or releases that session's execution and reservation.
6. Praebere unloads the model if it was loaded for this session and no other session requires it.
7. Pontis returns the terminal preparation failure to Repetere.
8. Repetere records the Run as `TERMINATED` with the returned reason.
9. Repetere does not start Vestigare and does not send replay traffic to Moderari.

Rollback must be safe when an earlier operation never completed. It must also be idempotent.

## 9. Failure response and terminal state

Where Pontis assigned a session before the failure, its response includes that session ID for operational evidence. Repetere does not use it to perform dependency-specific cleanup.

Example:

```json
{
  "status": "terminated",
  "session_id": "session-repetere-...",
  "termination_reason": "MODEL_LOAD_FAILED",
  "message": "The required Replay model could not be activated."
}
```

Repetere records one terminal state with a specific reason rather than introducing a separate top-level state for every failure:

```text
TERMINATED · MODEL_LOAD_FAILED
```

Recognised preparation reasons are:

```text
SOURCE_MODEL_MISSING
MODEL_NOT_AVAILABLE
MODEL_SELECTION_REJECTED
MODEL_RESERVATION_CONFLICT
TOOL_PROVIDER_CONNECTION_FAILED
MODEL_ACTIVATION_FAILED
MODEL_LOAD_FAILED
SESSION_PREPARATION_TIMED_OUT
DEPENDENCY_PROTOCOL_ERROR
```

## 10. Required Repetere changes

- Add `PREPARING` and `RUNNING_COMPARISON` operational states.
- Send the single Pontis session-preparation command.
- Use an outer configurable preparation timeout.
- Store only the Pontis-assigned session ID and active outcome.
- Start Vestigare only after Pontis reports `ACTIVE`.
- Remove direct model listing, selection, reservation and activation calls to Praebere.
- Remove direct model execution release calls to Praebere.
- On normal completion, stop Vestigare and request Pontis session closure.
- Record preparation failure as `TERMINATED` with a specific termination reason.

## 11. Required Pontis changes

- Implement the composite Replay session-start control operation.
- Generate the Repetere session ID internally.
- Create an empty authoritative session with origin `repetere`.
- Select and reserve the exact required model through Praebere.
- Eagerly create and bind the ACP tool-provider session after successful selection.
- Activate the model through Praebere.
- Report preparation progress to Repetere.
- Return only the session ID, model and active or terminated outcome required by Repetere.
- Roll back all partially created resources on failure.
- Preserve the existing Pontis-owned session-end and Praebere-release path.
- Ensure preparation does not create a fallback `session-http-...` session.

## 12. Expected package impact

| Package | Stage One work |
| --- | --- |
| Repetere | Composite start request, outer timeout, preparation state, removal of direct Praebere lifecycle ownership |
| Pontis | Composite operation, Pontis-assigned session, model orchestration, eager empty ACP binding and rollback |
| Nuntius | Existing routing plus verified long lifecycle timeout behaviour |
| Praebere | Existing model selection, reservation, activation and release contracts; no expected redesign |
| Vestigare | No preparation change; it starts only after successful activation |
| Moderari | No Stage One change expected |
| External tool provider | No change |

## 13. Manual acceptance tests

Every test begins by starting a real staged Replay in Repetere. No artificial Rogare command or standalone Repetere session is used.

### 13.1 Valid unloaded model

1. Ensure the recorded model is selected by no session and is not resident.
2. Start the Replay.
3. Verify Repetere shows `PREPARING`.
4. Verify Pontis creates exactly one `session-repetere-...` session.
5. Verify Praebere reserves the exact recorded model for that session.
6. Verify Pontis creates the ACP tool-provider binding without generating a conversation.
7. Verify Praebere loads and activates the model.
8. Verify Pontis reports the session `ACTIVE`.
9. Verify Repetere starts Vestigare only after activation.
10. Verify Repetere enters `RUNNING_COMPARISON` and the Replay runs normally.

### 13.2 Invalid or unavailable model

1. Use a source model identity that Praebere cannot select in the test environment.
2. Start the Replay.
3. Verify Pontis rejects and rolls back preparation.
4. Verify Repetere records `TERMINATED · MODEL_NOT_AVAILABLE` or the precise returned reason.
5. Verify Vestigare never starts.
6. Verify no Pontis session, ACP binding or Praebere reservation remains open.

### 13.3 Reservation conflict

1. Keep another session active with an incompatible selected model.
2. Start a Replay requiring a different model.
3. Verify Praebere rejects the new reservation without changing the existing session.
4. Verify Pontis rolls back only the new Replay session.
5. Verify Repetere records `TERMINATED · MODEL_RESERVATION_CONFLICT`.
6. Verify Vestigare never starts.

### 13.4 ACP tool-provider connection failure

1. Make the configured external tool provider unavailable.
2. Start the Replay with a valid model.
3. Verify model selection/reservation succeeds before ACP creation is attempted.
4. Verify ACP creation fails and Pontis follows its session-end rollback.
5. Verify Praebere releases the Replay reservation.
6. Verify Repetere records `TERMINATED · TOOL_PROVIDER_CONNECTION_FAILED`.
7. Verify Vestigare never starts.

### 13.5 Model activation or load failure

1. Cause activation of an available model to fail or exceed the configured lifecycle timeout.
2. Verify Pontis reports the correct activation/load failure.
3. Verify Pontis follows its session-end rollback.
4. Verify Praebere retains no reservation or active execution for the Replay session.
5. Verify Repetere records the specific `TERMINATED` reason.
6. Verify Vestigare never starts.

### 13.6 Successful matched Replay and cleanup

1. Start a Replay using a valid recorded model.
2. Verify preparation succeeds and the existing private Replay completes as a match.
3. Verify Repetere stops Vestigare.
4. Verify Repetere asks Pontis to close the session.
5. Verify Pontis closes its session and ACP resources.
6. Verify Pontis informs Praebere that the session terminated.
7. Verify Praebere releases the execution and reservation.
8. Verify Praebere unloads the model if no other session requires it.
9. Verify no fallback HTTP session or orphaned resource remains.
10. Verify the Run is `MATCHED · COMPLETED`.

## 14. Stage One completion criteria

Stage One is complete only when:

- A real Repetere Run creates exactly one Pontis-assigned session.
- The session is created without caller-provided identity or bootstrap metadata.
- Pontis owns all Praebere selection, reservation, activation and release operations.
- Repetere starts Vestigare and comparison only after Pontis reports `ACTIVE`.
- Existing private matched Replay behaviour still works.
- Every preparation failure follows the Pontis session-end rollback path.
- Repetere records a stable terminal reason for every failed preparation.
- No failed or completed Run leaves an ACP binding, Pontis session, Vestigare recording or Praebere reservation active.
