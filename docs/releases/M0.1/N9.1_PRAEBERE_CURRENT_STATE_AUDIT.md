# N9.1 — Praebere Current-State Audit

**Component:** Lumen Praebere  
**Source package audited:** `Lumen-Praebere-0.1.1-M1.1`  
**Date:** 2026-08-30  
**N9 milestone:** Praebere First Native Adoption  
**Status:** N9.1 complete

---

## 1. Purpose

N9.1 establishes the current Praebere implementation baseline before adding native
Nuntius provider/model discovery and selection.

The audit covers:

- current provider adapter/lifecycle code;
- provider/model configuration and state representation;
- existing discovery/model-selection capability that can be reused;
- duplicated provider/model knowledge that should not be propagated;
- the M0.1 model-selection scope.

The M0.1 selection decision is already settled:

> **Provider and selected-model state are runtime-global for M0.1.**

Per-session provider/model selection is optional polish/future development and is not
an N9 release blocker.

## 3. Current Architecture

Praebere is already well factored for N9.

Current layering is:

```text
FastAPI
  |
  v
PraebereService
  |
  v
ModelProvider protocol
  |
  v
OllamaProvider
  |
  +--> Ollama HTTP API
  |
  +--> ProviderLifecycle
          |
          v
      ProcessLifecycle
```

This is the correct boundary for N9:

- Lumen-facing service/API code is provider-neutral;
- Ollama endpoint knowledge remains in `providers/ollama.py`;
- provider process ownership remains in `ProcessLifecycle`;
- Servire can request aggregate lifecycle behaviour without learning Ollama-specific
  implementation details.

---

## 4. Current Configuration

Current `config.yaml` defines one provider and one configured model:

```yaml
provider:
  type: ollama
  endpoint: http://127.0.0.1:11434

model:
  name: qwen2.5-coder:14b-32k
  keep_alive: -1
```

Important findings:

- provider type is constrained to `Literal["ollama"]`;
- Ollama is therefore already the explicit M0.1 provider boundary;
- model identity is currently static configuration;
- the configured model is injected into `OllamaProvider` at construction time;
- there is no mutable runtime selected-model state;
- changing the selected model currently requires configuration/restart rather than an
  authoritative runtime operation.

This is the principal state-model change N9 must introduce.

---

## 5. Existing Provider State

Praebere currently distinguishes:

```text
Provider:
    stopped
    running

Configured model:
    unavailable
    available
    loaded
```

This is a useful N9 foundation.

`OllamaProvider.status()` already uses:

```text
GET /api/tags
GET /api/ps
```

to distinguish:

- provider reachability;
- locally available model;
- loaded/resident model.

The distinction required by N9 between model availability and readiness therefore
already exists for the **currently configured model**.

N9 should generalise this capability to discovered models rather than replace it.

---

## 6. Existing Provider Discovery Capability

There is no Lumen-level provider discovery operation yet.

However, the current configuration makes the M0.1 answer deterministic:

```text
supported provider type: ollama
configured endpoint:     provider.endpoint
runtime state:           stopped | running
```

Therefore `\obt providers` does not require a new provider registry for M0.1.

Praebere can authoritatively report its configured/supported Ollama provider through
the existing provider-neutral boundary.

Future multi-provider support should extend the provider-adapter layer rather than
change the Nuntius control contract.

---

## 7. Existing Model Discovery Capability

Praebere does not expose a `models` service operation today.

But `OllamaProvider` already retrieves `/api/tags` and contains model-name extraction
logic in `_model_names()`.

That logic is currently used only to determine whether the configured model exists.

N9 can reuse/generalise this path to expose the complete locally available model
catalogue.

Required extension:

```text
ModelProvider
    +--> models()

OllamaProvider.models()
    +--> GET /api/tags
    +--> provider-neutral model descriptors
```

Where useful, loaded/resident state can be correlated with `/api/ps`.

No caller outside Praebere should parse Ollama `/api/tags` or `/api/ps`.

---

## 8. Existing Model Selection Capability

There is currently **no runtime model-selection operation**.

The active model is effectively:

```text
config.model.name
```

and `OllamaProvider` stores that `ModelConfig` as `_model`.

Consequences:

- `status()` reports only the configured model;
- `load()` operates only on that model;
- `unload()` operates only on that model;
- lifecycle start loads that model;
- lifecycle stop unloads that model;
- no service method can change model identity;
- no API/control request can select another model;
- no authoritative selection acknowledgement exists.

N9 must convert model identity from a construction-time constant into explicit
runtime-global Praebere state.

The configuration should remain the **initial/default model selection**. It should not
remain the only possible model.

---

## 9. M0.1 Runtime-Global Selection

The existing architecture strongly supports the M0.1 decision to use global model
selection.

Praebere currently contains:

- one provider adapter instance;
- one configured model;
- one provider lifecycle;
- no session registry;
- no session-specific state.

Therefore the bounded N9 change is:

```text
Praebere runtime
    selected_provider = ollama
    selected_model = <model>
```

rather than:

```text
session_id -> provider/model state
```

A successful `\obt model select <model>` should update this one authoritative runtime
selection.

All subsequent consumers of Praebere model state must observe the same selected model.

Per-session selection would require a new ownership/lifetime model and is correctly
deferred.

---

## 10. Provider Lifecycle / Ownership

The existing lifecycle boundary is suitable and must be preserved.

Current behaviour:

- if Ollama is already externally running, Praebere may use it;
- detecting/using external Ollama does not acquire process ownership;
- `managed_process=false` prevents Praebere from stopping externally managed Ollama;
- if Praebere starts Ollama, `managed_process=true`;
- lifecycle stop unloads the configured model;
- lifecycle stop stops Ollama only if Praebere owns that process.

This matches the M0.1 requirement:

> Stack Stop releases/unloads Praebere-managed model resources and stops Ollama only
> when Praebere owns the Ollama process.

N9 must not weaken this behaviour while making model identity selectable.

---

## 11. Current HTTP Surface

Existing endpoints are:

```text
GET  /health
GET  /status

POST /operations/start
POST /operations/load
POST /operations/unload
POST /operations/stop

POST /lifecycle/start
POST /lifecycle/stop
```

There is currently:

- no `/control/obt` endpoint;
- no common Nuntius control request envelope;
- no command discovery/help catalogue;
- no provider query command;
- no model query command;
- no model-select command;
- no request/session/origin correlation handling;
- no Nuntius response semantics.

This makes Praebere a clean candidate for the intended **first native adoption**:
there is no legacy conversational `\obt` path that needs preserving or migrating.

---

## 12. Current Nuntius / Servire Integration

Praebere currently has no Nuntius-specific implementation.

N9 therefore needs to add the standard service-owned control surface, not adapt an
existing legacy command path.

Servire should supply:

- Praebere active endpoint;
- `obt_enabled`;
- command/service catalogue participation;
- configured response consumers where required.

Nuntius should learn Praebere commands from Praebere's service-owned catalogue and
route requests to Praebere.

Praebere itself should remain unaware of which external client originated the command
beyond the common request metadata required for correlation.

---

## 13. Current Rogare / Moderari Integration Boundary

No provider/model discovery result propagation exists in this package.

No code in Praebere currently:

- updates Rogare model-choice UI;
- updates Moderari selected-model execution state;
- broadcasts provider/model lists;
- manages client/session correlation.

That is good separation.

N9 should preserve it:

- Praebere produces authoritative provider/model results;
- Nuntius handles routing/correlation;
- Servire configuration determines any additional response consumers;
- Rogare/Moderari consume authoritative state;
- unrelated services do not receive provider/model lists.

---

## 14. Current Execution-Provenance Boundary

Praebere currently exposes model/provider status but does not write conversational
Trace evidence and is not in the model-data path.

The supplied package therefore does not establish:

- how selected provider/model identity reaches Vestigare;
- whether current Trace evidence contains model/provider identity;
- whether Repetere treats such identity as provenance or Replay binding.

That remains the already-defined N9/Repetere investigation boundary.

N9 should first make the selected provider/model authoritative and externally
observable. The cross-service provenance/replay work can then consume that authority
without inferring state from configuration files or UI selections.

---

## 15. Existing Code That Should Be Reused

The following implementation should be retained and extended rather than replaced:

### Provider adapter boundary

`ModelProvider` / `OllamaProvider`

### Ollama reachability

`OllamaProvider._get("/api/tags")`

### Ollama local-model discovery primitive

`OllamaProvider._model_names(...)`

### Ollama resident-model discovery primitive

`GET /api/ps`

### Model load/unload

`POST /api/generate`

with configured `keep_alive`

### Provider process ownership

`ProcessLifecycle.managed_process`

### Aggregate lifecycle

`PraebereService.lifecycle_start()`

`PraebereService.lifecycle_stop()`

### Existing state distinction

`unavailable | available | loaded`

These provide most of the provider-specific implementation required for N9.

## 16. Required N9 Structural Changes

The audit identifies these direct Praebere changes for N9.2 onward:

1. Introduce provider-neutral discovered-provider/model response models.
2. Extend `ModelProvider` with provider/model discovery operations.
3. Generalise Ollama `/api/tags` parsing into an authoritative model-list operation.
4. Introduce explicit runtime-global selected-model state.
5. Treat `config.model.name` as the initial/default selection.
6. Make status/load/unload/lifecycle operations use the runtime selected model.
7. Add validated runtime model selection.
8. Preserve the previous selection when selection fails.
9. Add the standard `/control/obt` endpoint.
10. Add service-owned command discovery/help.
11. Implement:
    - `\obt providers`
    - `\obt models`
    - `\obt model select <model>`
12. Add common Nuntius request/response/correlation semantics.
13. Add tests proving no Ollama-specific API details escape the adapter.
14. Preserve provider ownership/lifecycle semantics.
15. Update documentation after the control contract is live.

- establish effective provider/model provenance and Replay-binding behaviour after the

## 18. Audit Findings / Risks

### 18.1 Static model state is the main implementation constraint

The current configured-model object is shared deeply through status, load, unload and
lifecycle logic. Selection should therefore be introduced as a coherent state model,
not patched only into the command handler.

### 18.2 Do not make configuration mutable as runtime state

`config.yaml` should define initial/default selection. Runtime `model select` should
not rewrite configuration merely to make selection work.

### 18.3 Preserve availability versus residency

A model returned by `/api/tags` but absent from `/api/ps` is available but not loaded.
N9 UI/control responses should preserve that distinction.

### 18.4 Selection and readiness are separate

Selecting a model does not inherently mean it must already be resident. Praebere
should make the selection authoritative, then expose/perform readiness through its
provider-neutral lifecycle capability.

The exact point at which a newly selected model is loaded should remain explicit
during N9 implementation rather than be hidden inside unrelated callers.

### 18.5 External Ollama ownership must remain independent

Selecting/loading/unloading models on an externally running Ollama must never cause
Praebere to claim ownership of the provider process.
