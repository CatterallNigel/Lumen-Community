## 1. Purpose

This addendum groups the work that is specifically owned by, or must be validated while working in, **Moderari**. It allows Nuntius N7 migration and the remaining M0.1 Moderari work to be completed together where practical without changing the ordering or historical structure of the main M0.1 Development Roadmap.

The main roadmap remains authoritative for overall M0.1 scope. This document is a working extraction/checklist for the Moderari service pass.

## 2. N7 — Moderari Migration

**Objective:** Move Moderari-owned external control commands onto the explicit Nuntius control path.

### N7.1 Standard Control Endpoint

- [ ] Add the standard Moderari control endpoint used by Nuntius.
- [ ] Accept the common Nuntius control envelope, including request/session/origin correlation where supplied.
- [ ] Keep the normal model/data execution endpoint separate from the control endpoint.
- [ ] Ensure unsupported/unowned commands follow the common control response semantics rather than entering model execution.

### N7.2 Existing Handler Migration

- [ ] Identify existing Moderari `\\obt`/backchannel command handlers.
- [ ] Adapt Moderari-owned handlers to the common Nuntius response contract.
- [ ] Return `200` for successfully handled commands, with a body where the command is a query.
- [ ] Return `204` where Moderari legitimately has no response/responsibility under the common contract.
- [ ] Return explicit errors for malformed, invalid or failed Moderari-owned operations.
- [ ] Preserve request/session correlation on query responses.

### N7.3 Servire / Nuntius Registration

- [ ] Add/verify Moderari's `obt_enabled` capability in Servire configuration.
- [ ] Register Moderari-owned command tokens/routes in the Servire catalogue.
- [ ] Verify Nuntius receives the Moderari route when the service becomes available.
- [ ] Verify Nuntius removes/updates that route when Moderari stops or its catalogue state changes.
- [ ] Verify Moderari is reachable through Nuntius without broadcasting commands to unrelated services.

### N7.4 Temporary Compatibility

- [ ] Retain historical compatibility behaviour only where required during migration.
- [ ] Clearly separate compatibility handling from the new authoritative Nuntius path.
- [ ] Ensure the compatibility path cannot cause duplicate command execution.
- [ ] Mark compatibility behaviour for removal once all callers use Nuntius.

### N7.5 Trace / Context Safety

- [ ] Verify client-originated `\\obt` commands routed to Moderari do not enter ordinary model ask/answer execution.
- [ ] Verify historical Moderari control/backchannel traffic cannot leak into model conversational context.
- [ ] Verify control commands do not appear as conversational turns in Vestigare Trace.
- [ ] Where a control action changes an execution condition, ensure the resulting effective condition remains observable as execution evidence.

**N7 exit condition:** Moderari-owned external commands arrive through Nuntius rather than through ordinary model execution, and historical control traffic cannot contaminate model context or conversational Trace.

## 3. N7+ — Moderari System-Prompt Policy

These are existing M0.1 Moderari requirements that should be addressed while Moderari is already under active development.

### 3.1 Required Policy Modes

- [ ] Implement **Pass-through**.
- [ ] Preserve **Moderari Default** as the normal/default behaviour.
- [ ] Implement **Custom** as an exact researcher-defined system-prompt condition.

### 3.2 Pass-through

- [ ] Do not replace or alter a client-supplied system prompt.
- [ ] If the client supplies no system prompt, do not create one merely because Pass-through is selected.
- [ ] Verify Pass-through leaves client-controlled system context unchanged.
- [ ] Keep context compaction/checkpoint behaviour independent of system-prompt Pass-through.

### 3.3 Moderari Default

- [ ] Preserve current Moderari default system-prompt behaviour.
- [ ] Remove/supersede an incoming client system prompt where required by Default mode.
- [ ] Inject the Moderari Default system prompt exactly as intended by the existing normal Lumen path.
- [ ] Preserve any existing Default-mode tool-related system-prompt processing until deliberately redesigned.

### 3.4 Custom

- [ ] Remove/supersede the incoming client system prompt.
- [ ] Inject the researcher-defined Custom prompt.
- [ ] Do not add, remove, rewrite, merge, normalise or otherwise augment the selected Custom prompt.
- [ ] Do not carry tool instructions/descriptions from the removed client system prompt into Custom.
- [ ] Keep tool availability separate from tool instructions contained in the Custom prompt.
- [ ] Require any desired tool descriptions/tool-use instructions to be explicitly present in the researcher-defined Custom prompt.
- [ ] Verify a Custom prompt without tool instructions is not silently augmented when tools are available.
- [ ] Verify a Custom prompt containing researcher-supplied tool instructions does not acquire a second Moderari-generated tool block.

**Policy exit condition:** system-prompt behaviour is explicit, selectable and reproducible; Custom is demonstrably the exact researcher-defined prompt rather than a Moderari-generated or tool-augmented derivative.

## 4. N7+ — Moderari-Owned System-Prompt UI

- [ ] Implement the System Prompt Policy UI as a **Moderari-owned operational surface**.
- [ ] Expose that Moderari UI within Servire's Moderari tab without making Servire a control intermediary.
- [ ] Present Pass-through / Moderari Default / Custom selection clearly.
- [ ] Add explicit editor **working-copy** versus **active-runtime-state** visibility.
- [ ] Require explicit **Apply** before Custom editor contents become Moderari's active prompt.
- [ ] Treat Apply as a local Moderari configuration action rather than an unnecessary Servire/Nuntius round trip.
- [ ] Disable or hide Custom-only controls when Custom mode is not selected, where appropriate.

---

## 5. N7+ — Saved Custom System Prompts

### 5.1 Persistence

- [ ] Add a dedicated MongoDB collection for Moderari saved system prompts.
- [ ] Define a minimal schema containing stable `prompt_id`, human-readable `name`, `content`, `owner_id`, `scope`, `created_at`, and `updated_at`.
- [ ] Use a simple/default M0.1 owner identity while retaining `owner_id` for future compatibility.
- [ ] Retain an explicit `scope` field without implementing multi-user/organisational policy in M0.1.

### 5.2 Editor / Saved Object / Runtime Separation

- [ ] List/select saved prompts.
- [ ] Load a selected prompt into the Custom editor as a working copy.
- [ ] Ensure editing the working copy does not mutate the saved object or active runtime configuration.
- [ ] Implement **Apply** independently of persistence.
- [ ] Implement **Save As…** to create a new saved prompt without overwriting the source prompt.
- [ ] Implement explicit **Update Saved**.
- [ ] Implement explicit **Delete Saved**.
- [ ] Ensure Save As…, Update Saved and Delete Saved do not silently alter Moderari's active runtime prompt.
- [ ] Ensure Apply does not silently create or update a saved prompt.
- [ ] Do not store active runtime state as an `is_active` property of a saved-prompt document.

### 5.3 Deliberate M0.1 Boundary

Do **not** add prompt sharing, organisational prompt libraries, mandatory organisational prompts, permission policy or sophisticated prompt version history in M0.1.

**Saved-prompt exit condition:** researchers can safely reuse and modify controlled system-prompt conditions while saved definitions, editor working copies and Moderari's active runtime configuration remain explicit and independent.

## 6. N7+ — Effective System-Prompt Trace Provenance

Live testing during the preceding N6/Vestigare work established that the effective Moderari Default system prompt is **not currently represented authoritatively enough in Trace for Replay fidelity**. This is therefore active M0.1 work rather than a theoretical validation item.

- [ ] Validate baseline/Default, Pass-through and Custom executions against Vestigare Trace.
- [ ] Ensure Trace unambiguously identifies the **effective system prompt that actually reached the model**.
- [ ] Where Moderari supersedes an incoming client system prompt, preserve the incoming prompt as provenance if available, but distinguish it from the active/effective prompt.
- [ ] Ensure a superseded incoming prompt cannot later be mistaken for Replay input.
- [ ] If the execution path does not naturally expose the effective prompt to Vestigare, implement the minimum explicit provenance mechanism required.
- [ ] Prefer the established control architecture for any explicit notification: Moderari → Nuntius → appropriate consumer, correlated to the model/session execution.
- [ ] Ensure any such provenance/control notification remains outside conversational Trace turns.
- [ ] Retain the actual applied Custom prompt in Trace regardless of later saved-prompt changes or deletion.

**Trace-provenance exit condition:** the Trace provides authoritative evidence of exactly which system prompt reached the model, while preserving any superseded incoming prompt only as distinguishable provenance.

## 7. N7+ — Replay Pass-through Prerequisite

This work crosses the Moderari/Repetere boundary. The Repetere side remains tracked in the N6+ addendum; this section records the Moderari-owned side that should be implemented/validated while Moderari is open.

- [ ] Provide a Moderari control command that allows Repetere to establish the required Replay Pass-through condition through Nuntius.
- [ ] Return an authoritative positive acknowledgement (`200`) only when the required Moderari state has actually been established.
- [ ] Ensure failure, invalid state or inability to establish the prerequisite produces an explicit non-success response.
- [ ] Ensure Repetere can require that acknowledgement before any Replay model interaction begins.
- [ ] Ensure Replay does not silently substitute the current Moderari Default or current saved/Applied Custom prompt for the source Trace's effective prompt.
- [ ] Ensure Replay reconstructs exactly one active effective system prompt.
- [ ] Ensure a superseded incoming prompt and its Moderari replacement are never both reconstructed as active prompts.

### M0.1 Shared-Execution-Condition Constraint

The Replay control design must remain consistent with the M0.1 concurrent-session rule: concurrent sessions share the provider/model and Moderari system-prompt execution condition established by the first active session. Do not introduce a hidden per-session execution-condition model during N7 unless the main M0.1 requirements are deliberately revised.

**Replay/Moderari exit condition:** Repetere can establish and verify the Moderari prerequisite needed for faithful Replay through Nuntius without contaminating other execution state or model context under the supported M0.1 session rules.

## 8. N7+ — Context Compaction Preservation

N7 changes must not accidentally alter Moderari's existing context-management responsibility.

- [ ] Preserve checkpoint/context-compaction behaviour during the control migration and system-prompt-policy changes.
- [ ] Preserve the approximately 63% context-utilisation checkpoint threshold unless separately changed by an explicit requirement.
- [ ] Preserve use of the two most recent checkpoints in continuing compacted context.
- [ ] Keep context compaction independent of Pass-through / Default / Custom policy selection.
- [ ] Verify the effective compacted execution context remains observable through Vestigare.

---

## 9. N7+ — Concurrent Session Rules

- [ ] Verify session-specific conversational context remains isolated across simultaneous sessions.
- [ ] Verify Moderari control responses remain correlated to the originating request/session where correlation is applicable.
- [ ] Validate the M0.1 rule that the **first active session establishes the shared Moderari system-prompt condition** for concurrent sessions.
- [ ] Verify a subsequent concurrent session cannot change the Moderari system-prompt policy or Applied Custom prompt while another session remains active.
- [ ] Verify no Moderari migration or compatibility path causes session-specific conversational content to cross between clients.

Independent per-session provider/model/system-prompt conditions remain future development and are not to be introduced implicitly as part of N7.

---

## 10. Validation Matrix

Before Moderari is considered complete for this service pass, validate at minimum:

- [ ] `pytest` passes.
- [ ] `ruff check .` passes.
- [ ] `mypy src tests` passes.
- [ ] Servire validates and starts Moderari normally.
- [ ] Moderari registers correctly with the Servire/Nuntius control catalogue.
- [ ] A Moderari-owned `\\obt` command reaches Moderari through Pontis → Nuntius → Moderari.
- [ ] The response returns through Nuntius to the correct originating caller where applicable.
- [ ] The same control traffic is absent from model conversational context and Trace turns.
- [ ] Default policy executes correctly.
- [ ] Pass-through executes correctly.
- [ ] Custom executes exactly the Applied prompt.
- [ ] Effective system-prompt provenance is visible and unambiguous in Trace for all three policy modes.
- [ ] Saved-prompt operations do not silently change active runtime state.
- [ ] Replay prerequisite control can be positively acknowledged by Moderari through Nuntius.
- [ ] Existing normal ask/answer behaviour remains operational after migration.

## 11. Completion Boundary

Completing **N7** itself means the Moderari-owned external command path has migrated to Nuntius safely.

Completing this **N7+ Moderari service pass** additionally means that the Moderari-specific M0.1 work that is practical to implement while the service is open has been completed or explicitly marked as blocked by another service/dependency.

Cross-service work must not be marked complete merely because the Moderari side exists. In particular, full Replay fidelity remains dependent upon Repetere, Vestigare evidence, and integrated validation.
