## Purpose

This addendum extracts the M0.1 requirements that are specifically owned
by **Repetere**, so that the N6 control-plane migration can be used as
the point at which all currently unblocked Repetere-local M0.1 work is
completed.

It does **not** replace or reorder the main M0.1 Development Roadmap.
The parent roadmap remains the authoritative dependency-driven release
plan. This document is an implementation checklist for a service-focused
development pass.

The working principle is:

> When a roadmap dependency makes a service ready for modification,
> complete all currently unblocked M0.1 work owned by that service
> before leaving it. Requirements that depend on unfinished work in
> another service remain explicitly blocked and stay on the parent
> roadmap.

## N6+ --- Repetere M0.1 Requirements

### A. N6 --- Nuntius Control-Plane Migration

-   [x] Add the standard Repetere `/control/obt` endpoint.

-   [x] Consume Repetere-owned `\obt` commands locally rather than
    allowing them to continue through the ordinary proxy/model execution
    path.

-   [x] Migrate existing Repetere `\obt` behaviour to the common Nuntius
    control path.

-   [x] Return the authoritative Repetere result through Nuntius to the
    originating Pontis/client session.

-   [x] Preserve request/session correlation.

-   [x] Ensure Repetere control traffic remains outside the ask/answer
    Trace path.

-   [x] Ensure a Repetere-owned control request does not traverse onward
    to Moderari.

-   [x] Preserve existing ordinary Repetere request/proxy behaviour.

-   [x] Validate the live path with the existing acceptance command:

    `\obt repetere list`

    **Validated live:** Repetere consumed the request locally and returned
    the authoritative prepared-Replay list through Nuntius/Pontis. The earlier
    pre-N6 `404 Not Found` was eliminated. Ordinary ask/answer traffic remained
    functional.


**N6 status:** **COMPLETE.** Unit/regression tests, Ruff and mypy were clean,
and the live `\obt repetere list` path was exercised from Rogare. The same
external-client return boundary was subsequently validated from Pi through
Pontis HTTP.

### B. Replay Session Isolation

**Status 2026-08-26:** not yet claimed complete. N6 concentrated on the control
migration. These items remain explicit Repetere-local work unless code inspection
at the next Repetere touch confirms they are already guaranteed.

-   [ ] Require every Replay execution to create a **new isolated Replay
    session**.
-   [ ] Initialise the Replay session only from the source Trace and
    explicitly defined experimental conditions.
-   [ ] Ensure sequential Replay runs do not inherit conversational
    context or temporary state from a preceding Replay.
-   [ ] Ensure every future Experiment run receives its own Replay
    session rather than reusing another run's session.
-   [ ] Add regression coverage proving sequential Replay executions are
    isolated.

### C. Effective System-Prompt Replay

These requirements are Repetere-owned, but some cannot be completed
until the Vestigare/Moderari system-prompt investigation establishes
exactly which prompt representation is authoritative.

-   [ ] Determine which system-prompt record Repetere currently
    reconstructs.
-   [ ] Determine whether Replay can currently send two active system
    prompts.
-   [ ] Replay the **effective system prompt captured in the source
    Trace**.
-   [ ] Never substitute the current Moderari Default prompt for the
    source Trace's effective prompt.
-   [ ] Never substitute the current saved/applied Moderari Custom
    prompt for the source Trace's effective prompt.
-   [ ] Reconstruct exactly **one** active effective system prompt.
-   [ ] Exclude a superseded incoming system prompt from Replay
    reconstruction while retaining it as provenance where the Trace
    representation supports that distinction.
-   [ ] Add a deliberately system-prompt-sensitive behavioural
    validation capable of exposing duplicate or incorrect system
    context.

**Finding 2026-08-26:** a fresh recorded execution established that the Trace
contains system-role content, but **does not unambiguously persist the authoritative
post-Moderari Default system prompt** that actually reached the model. The prompt
visible in later provider-side traffic can be Pi/client context rather than the
Moderari effective prompt. Therefore Default Replay fidelity currently fails the
Trace-evidence requirement. Custom is expected to have the same transformation
problem; Pass-through still needs explicit validation.

**Dependency:** final implementation/acceptance is blocked until the N7 Moderari
pass emits/preserves the authoritative effective prompt and Vestigare stores it
in a form Repetere can reconstruct without inference.

### D. Moderari Pass-through Coordination

Repetere owns initiation of the Replay condition; Moderari owns
implementation of the session-scoped override.

-   [ ] For each new Replay session, issue the Moderari **Pass-through
    override through Nuntius** before model interaction begins.
-   [ ] Preserve the Replay session/request identity in that control
    exchange.
-   [ ] Require positive Moderari acknowledgement before beginning
    Replay model interaction.
-   [ ] Treat failure to establish the required Pass-through condition
    as a failed/incomplete Replay rather than silently continuing.
-   [ ] Verify Replay cannot begin under the current
    global/default/custom Moderari condition when the session-scoped
    Replay override has not been acknowledged.

**Dependency:** blocked until **N7** exposes the corresponding Moderari
Nuntius-owned session-scoped Pass-through control operation. This is the next
planned cross-service dependency.

### E. Provider / Model Replay Behaviour Investigation

The parent roadmap requires the existing Repetere behaviour to be
established rather than silently assuming a binding policy.

-   [ ] Determine whether Repetere reads or acts upon provider/model
    identity recorded in the source Trace.
-   [ ] Determine whether provider/model identity appears indirectly in
    reconstructed system, assistant, or other conversational messages.
-   [ ] Test whether the same source Trace can be replayed against a
    different selected provider/model without otherwise changing its
    recorded conversational context.
-   [ ] Inspect what is sent to the alternate model.
-   [ ] Inspect what the resulting Vestigare Trace records.
-   [ ] Establish explicitly whether provider/model identity is
    descriptive provenance, Replay-binding information, or both.
-   [ ] Leave no unsupported provider/model binding or substitution
    guarantee implicit for M0.1.

**Dependency:** investigation spans Repetere, Vestigare and the active
provider/model selection path. It remains open and is best completed once the
Praebere provider/model command path is native on Nuntius, so cross-model testing
uses the intended M0.1 control surface rather than a temporary path.

### F. Experiment / Run Integration Preparation

The Experiment concept belongs to the later M0.1 Experiment Structure
phase, but Repetere owns several parts of the execution evidence.

-   [ ] Associate replay-created Traces with Experiment runs when the
    Experiment relationship is introduced.
-   [ ] Surface each run state as `MATCHED`, `DIVERGED`, or
    `FAILED / INCOMPLETE`.
-   [ ] Surface the first divergence point where available.
-   [ ] Preserve the distinction between **Repetere divergence
    detection** and future **Aestimare assessment**.
-   [ ] Ensure Repetere's session-isolation design is ready for
    Fiducia-coordinated repeated execution.

**Dependency:** final wiring is blocked by the Experiment/Fiducia work.
Do not create a parallel Repetere-only Experiment mechanism during N6+. Existing
Repetere divergence reporting remains useful baseline capability, but it is not
by itself completion of the Experiment/run relationship.

## N6+ Exit Condition

**Current status: N6 COMPLETE; Repetere M0.1 service-local completion remains open.**

Repetere may be considered **N6 complete** when:

1.  `\obt repetere ...` commands arriving through Pontis → Nuntius are
    consumed by Repetere's control endpoint;
2.  they no longer traverse the ordinary Repetere → Moderari model path;
3.  authoritative results return through Nuntius to the correct
    originating session;
4.  ordinary non-control requests remain unaffected; and
5.  unit tests, regression tests, Ruff and mypy are clean.

All five N6 conditions have been demonstrated.

Repetere may be considered **M0.1 service-local complete** when, in
addition:

1.  every Replay execution begins in a fresh isolated Replay session;
2.  sequential runs cannot inherit prior Replay context/state;
3.  Repetere's current system-prompt reconstruction and provider/model
    behaviour have been explicitly established;
4.  all Repetere-owned work that does not depend on unfinished Moderari,
    Vestigare, Fiducia or Experiment functionality has been completed;
    and
5.  remaining blocked requirements are explicitly identified for later
    cross-service integration rather than hidden as unfinished Repetere
    work.

## N6+ Discoveries Carried Forward to N7 and Later

- **Effective system-prompt evidence is a real defect, not merely an investigation.**
  Moderari Default currently cannot be replayed faithfully from Trace evidence alone.
- **Vestigare recording semantics are now explicit:** one active M0.1 recording,
  one bound session, one owner. Other sessions continue but are excluded from that Trace.
- **Trace ownership UI/state is event-driven through Nuntius:** Rogare and Vestigare
  no longer need a new five-second Trace-status polling loop.
- **Initial Trace-state resynchronisation remains defective:** Rogare's one-time
  `\obt vestigare trace status` currently receives `404` through Nuntius. Push events
  work, but reconnect/reload recovery must be fixed.
- **Fiducia lifecycle follow-up:** stale PID handling is recurring and `clear-logs`
  is incompatible with the current Fiducia CLI. Treat both in the same lifecycle/CLI pass.
- **Optional polish:** if time during Moderari work, migrate heartbeat/progress status
  delivery from the historical Pontis/Rogare polling path to Nuntius. This is separate
  from the now-completed Trace ownership messaging.

## Roadmap Maintenance Convention

The main M0.1 Development Roadmap should remain the release-level source
of truth.

As each service-focused pass is completed:

-   mark the corresponding completed items in the main roadmap;
-   leave dependency-blocked items unchecked;
-   reference the relevant service addendum where useful;
-   do not remove completed requirements from the main roadmap;
-   use the same service-focused extraction strategy for later services
    where it reduces repeated code archaeology and context switching.

The next obvious candidate is **Moderari**, because its control
migration, Replay Pass-through support, system-prompt policy, UI and
saved-prompt responsibilities span several roadmap phases.
