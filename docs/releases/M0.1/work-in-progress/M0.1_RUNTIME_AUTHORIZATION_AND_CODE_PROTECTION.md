# M0.1 Runtime Authorization and Code Protection

## Status

**Release:** Lumen M0.1  
**Purpose:** External / Research Distribution  
**Scope:** Runtime authorization, service lifecycle control, configuration protection, installation identity, and distribution security.

---

## 1. Purpose

The M0.1 external research distribution must assume that once Lumen source code has been distributed, that distribution cannot practically be withdrawn.

The security objective is therefore not to make the distributed software impossible to inspect or modify. Any software executing on hardware outside Illuminates.One's control must ultimately be considered accessible to a sufficiently determined operator.

Instead, M0.1 establishes a controlled runtime model in which:

- an authorised Lumen installation must periodically establish authorization with Illuminates.One;
- authorization communication occurs over TLS/HTTPS;
- installations possess a cryptographic identity in addition to their Service Group UUID;
- Illuminates.One cryptographically signs runtime authorization;
- Lumen services are started and supervised through **Lumen Servire**;
- distributed service configuration is protected at rest;
- valid runtime authorization is required before protected configuration becomes usable;
- copied or redistributed installations should not automatically become functional Lumen installations;
- ordinary execution of an unmodified distribution remains dependent upon its authorised installation identity.

The mechanism should provide meaningful technical protection while avoiding reliance upon legal enforcement as the primary control.

---

## 2. Security Principle

The fundamental rule is:

> **Possession of the distributed source code must not, by itself, constitute authorization to operate a Lumen installation.**

Authorization is associated with a recognised Lumen installation and maintained through communication with Illuminates.One.

Technical controls should make unauthorized execution or redistribution deliberate rather than accidental.

They are not intended to provide an absolute DRM mechanism.

---

## 3. Installation Identity

Each externally distributed Lumen environment should have several distinct identifiers.

### 3.1 Distribution ID

Identifies the particular release artifact issued by Illuminates.One.

For example:

```text
distribution_id: lumen-research-m0.1-xxxxx
```

The Distribution ID establishes provenance for the package that was supplied.

### 3.2 Service Group UUID

Each installed Lumen stack has a unique **Service Group UUID**.

The Service Group UUID identifies the authorised installation as a whole rather than any individual Lumen service.

Servire is responsible for presenting this identity to Illuminates.One.

However:

> **The Service Group UUID is an identifier, not an authentication secret.**

Knowledge of another installation's Service Group UUID must not be sufficient to impersonate that installation.

### 3.3 Installation Cryptographic Identity

Each authorised installation should additionally possess its own cryptographic identity.

During provisioning, Servire should generate or receive an installation-specific public/private key pair.

The intended ownership is:

```text
Installation Private Key
        │
        └── retained by the authorised installation

Installation Public Key
        │
        └── registered with Illuminates.One
```

The installation private key must never be transmitted to Illuminates.One during normal operation.

Illuminates.One associates the registered public key with the corresponding Service Group UUID and Distribution ID.

This allows Illuminates.One to authenticate an installation cryptographically rather than trusting possession of a UUID.

### 3.4 Service Instance Identity

Individual services may additionally have their own service or instance identifiers.

These identities allow runtime and trace provenance to be associated with:

```text
Distribution
    ↓
Installation / Service Group
    ↓
Service
    ↓
Execution / Trace
```

---

## 4. Servire as Operational Authority

For an external M0.1 distribution, **Lumen Servire is the operational authority for the service group**.

Normal service lifecycle operations must therefore occur through Servire.

The intended lifecycle is:

```text
Operating System
      │
      ▼
   Servire
      │
      ├── establish authorization
      ├── unlock runtime configuration
      ├── validate dependencies
      ├── start services
      ├── supervise services
      └── stop/restart services
```

Individual Lumen services should not be considered validly started merely because their executable, Python module, HTTP server or entry point has been invoked directly.

Direct command-line execution is a development capability and should not form part of the supported M0.1 external runtime model.

---

## 5. Service Startup Authorization and Runtime Lease

Each protected Lumen service must be capable of determining that its startup was authorised by Servire.

The design must ensure that simply discovering and executing the underlying service command does not constitute normal authorised startup.

For the external M0.1 distribution, Servire should issue a **service-specific, short-lived runtime lease** whenever it starts a protected Lumen service. A service must validate that lease before becoming operational.

The trust chain is therefore:

```text
Illuminates.One
      │
      │ signed installation authorization lease
      ▼
   Servire
      │
      │ derives local runtime authority
      │
      ├── Moderari lease
      ├── Praebere lease
      ├── Trace lease
      ├── Replay lease
      └── other authorised service leases
```

The service lease should be cryptographically derived or authenticated using established cryptographic primitives. It must not be constructed using an ad-hoc formula such as simple concatenation of the Illuminates.One token with local values.

The Illuminates.One authorization should contribute to Servire's ability to establish runtime authority, while installation-local material should ensure that possession of a captured Illuminates.One response alone is insufficient to reproduce the service leases.

A service lease should be bound to information including, where applicable:

```text
service_group_uuid
distribution_id
service_name
service_instance_id
issued_at
expires_at
nonce
capabilities
```

This binding should ensure that:

- a lease issued to one service cannot authorize another service;
- a lease issued to one service group cannot authorize another service group;
- a lease issued to one service instance cannot automatically authorize another instance;
- an expired lease cannot be reused indefinitely;
- a captured launch exchange cannot become a permanent bypass mechanism.

A service must not contain everything required to authorize itself or another service.

In particular:

> **Servire holds operational authority; individual Lumen services do not inherit Servire's authority.**

Services may request lifecycle actions through Servire, but should not independently start other protected services.

### 5.1 Service Lease Renewal

Service authorization should continue beyond initial process startup.

While Servire's own Illuminates.One authorization remains valid, Servire should periodically renew each running service's short-lived runtime lease.

A service should therefore maintain a local authorization state such as:

```text
STARTING
    ↓
SERVIRE_LEASE_VALID
    ↓
RUNNING
    ↓
RENEWAL_DUE
    ↓
GRACE
    ↓
LEASE_EXPIRED
```

The service must not assume that successful startup grants permanent authority to continue operating.

If Servire can no longer provide valid lease renewal, the service should eventually enter its defined expired state and cease authorised operation.

The precise renewal interval and grace behaviour remain implementation decisions, but service leases should normally be substantially shorter-lived than the Illuminates.One-to-Servire authorization lease because renewal occurs locally.

### 5.2 Chained Lease Model

The external runtime therefore uses a chained authorization model:

```text
Illuminates.One
      │
      │ longer-lived signed authorization lease
      ▼
   Servire
      │
      │ short-lived local runtime leases
      ▼
Lumen Services
```

The governing principle is:

> **Illuminates.One leases authority to Servire. Servire leases authority to each Lumen service. No externally distributed service possesses permanent independent authority to operate.**

Individual services do not need access to the Illuminates.One authorization token itself. They receive only the service-specific authority required for their own operation.

This preserves separation of responsibility and reduces the value of credentials captured from any individual service.

---

## 6. Secure Communication with Illuminates.One

All authorization and heartbeat communication between Servire and Illuminates.One must occur over **TLS/HTTPS**.

TLS provides:

- confidentiality in transit;
- integrity in transit;
- authentication of the Illuminates.One HTTPS endpoint;
- protection against passive interception;
- protection against ordinary modification of requests and responses in transit.

TLS is, however, only one layer of the authorization architecture.

The authorization itself should also be cryptographically signed so that its authenticity can be independently verified by Servire.

The governing principle is:

> **TLS protects the communication channel. Digital signatures protect the authorization itself.**

---

## 7. Illuminates.One Signing Identity

Illuminates.One should maintain a dedicated authorization signing public/private key pair.

### Private Key

The **private signing key** remains exclusively on infrastructure controlled by Illuminates.One.

It must never:

- be distributed with Lumen;
- be embedded in Servire;
- appear in containers;
- appear in configuration files supplied to researchers;
- be transmitted to an installation.

### Public Key

The corresponding **public verification key** may safely be distributed with Servire.

Servire uses this public key to verify that authorization responses were genuinely issued by Illuminates.One.

Possession of the public key permits verification but does not permit creation of valid authorization responses.

This provides protection even if an attacker attempts to redirect Servire to a substitute authorization server.

Without the Illuminates.One private signing key, the substitute server cannot manufacture an authorization that an unmodified Servire will accept.

---

## 8. Bidirectional Cryptographic Identity

The complete authorization model should eventually provide cryptographic identity in both directions.

### Servire → Illuminates.One

Servire signs its authorization request using the installation private key.

Illuminates.One verifies that signature using the installation public key registered against the Service Group UUID.

This establishes:

> **This request originated from the cryptographic identity associated with this authorised installation.**

### Illuminates.One → Servire

Illuminates.One signs the authorization response using the Illuminates.One authorization private key.

Servire verifies the response using the Illuminates.One public key distributed with Lumen.

This establishes:

> **This authorization was genuinely issued by Illuminates.One.**

The exchange therefore provides mutual cryptographic attribution independently of the TLS transport layer.

---

## 9. Authorization Exchange

A normal authorization exchange may operate as follows:

```text
Servire
   │
   │ generate nonce
   │
   │ construct request
   │
   │ sign request with
   │ installation PRIVATE KEY
   │
   ▼
HTTPS / TLS
   │
   ▼
Illuminates.One
   │
   │ verify installation signature
   │ verify Service Group UUID
   │ verify Distribution ID
   │ verify authorization state
   │ verify request freshness
   │
   │ construct authorization
   │
   │ sign with Illuminates.One
   │ PRIVATE KEY
   │
   ▼
HTTPS / TLS
   │
   ▼
Servire
   │
   │ verify Illuminates.One signature
   │ verify nonce
   │ verify installation identity
   │ verify expiry
   │
   ▼
AUTHORIZED / REJECTED
```

A request may contain information including:

```text
service_group_uuid
distribution_id
servire_version
release_version
timestamp
nonce
service_manifest_hash
installation_public_key_identifier
```

No unnecessary personally identifying information should be transmitted.

---

## 10. Nonce-Based Challenge

Each authorization request should contain a cryptographically secure random nonce generated by Servire.

Illuminates.One includes that nonce in the signed authorization response.

Conceptually:

```text
Servire
   │
   │ UUID
   │ Distribution ID
   │ timestamp
   │ nonce A7F2...
   │ signed request
   ▼
Illuminates.One
   │
   │ authenticate installation
   │ validate authorization
   ▼
signed authorization
   │
   │ UUID
   │ nonce A7F2...
   │ issued time
   │ expiry
   ▼
Servire
```

The nonce ensures that recording a previous successful exchange does not allow that response to be reused as a valid response to a later authorization request.

---

## 11. Authorization Token

The authorization response does not need to resemble a human-entered authenticator code.

It should be a cryptographically signed token or assertion containing sufficient entropy and integrity protection.

Conceptually it may assert:

```text
installation = <service-group-uuid>
distribution = <distribution-id>
nonce = <request-nonce>
issued_at = <timestamp>
expires_at = <timestamp>
capabilities = [...]
```

Servire must verify the complete signed authorization before accepting it.

The implementation should use established cryptographic standards and libraries rather than custom cryptographic algorithms.

A modern digital-signature mechanism such as **Ed25519** is a suitable candidate for evaluation because of its small keys and signatures, strong security properties, performance, and widespread library support.

The final cryptographic choice should nevertheless be treated as an implementation/security decision rather than being permanently mandated by this architectural document.

---

## 12. Authorization Lease

Runtime authorization should use a **lease model** rather than requiring continuous connectivity.

A successful authorization grants the installation a limited operating lease.

Possible states are:

```text
AUTHORISED
    ↓
RENEWAL_DUE
    ↓
GRACE
    ↓
EXPIRED
```

Servire attempts to renew the lease periodically.

Temporary failures such as:

- Internet interruption;
- temporary Illuminates.One outage;
- DNS failure;
- local network disruption;

must not immediately terminate legitimate research work.

However, persistent inability to obtain authorization eventually causes the lease to expire.

Once the permitted grace period has expired, Servire must prevent continued authorised operation in accordance with the release policy.

The exact lease and grace durations should remain configurable on the Illuminates.One side and should not be permanently encoded as product policy within M0.1.

---

## 13. Deliberate Heartbeat Suppression

Failure of the authorization heartbeat and deliberate suppression of the heartbeat should ultimately have the same security consequence once the authorization lease expires.

The M0.1 design principle is:

> **An externally distributed Lumen installation must not continue operating indefinitely without authorization from Illuminates.One.**

The system should nevertheless distinguish normal temporary connectivity failures from malformed, invalid, rejected or cryptographically unverifiable authorization responses for operational diagnostics.

A cryptographically invalid response must never extend an authorization lease.

---

## 14. Installation Private-Key Protection

The installation private key necessarily exists within an environment outside Illuminates.One's direct control.

It must therefore be treated differently from the Illuminates.One private signing key.

Where available, installation private-key storage should prefer:

1. hardware-backed or TPM-backed key storage;
2. operating-system credential/key storage;
3. protected encrypted local storage controlled by Servire.

The private key should not be stored as a normal plaintext configuration value.

The architecture must nevertheless recognise that an operator with sufficient control over the installation may ultimately be capable of extracting or bypassing locally held credentials.

Installation keys therefore provide strong installation identity and resistance to casual copying, but must not be represented as an absolute hardware trust boundary unless hardware-backed protection is actually used.

---

## 15. Protected Service Configuration

Service configuration included with an external release should be encrypted at rest wherever it contains protected operational information.

Plaintext configuration required for normal startup should not simply reside beside the service executable.

Conceptually:

```text
Encrypted Configuration
        │
        ▼
      Servire
        │
   valid authorization
        │
        ▼
 runtime decryption
        │
        ▼
     Service
```

Where practical, decrypted configuration should exist only in memory and should not be written back to persistent storage as plaintext.

---

## 16. Key Management Principle

Encryption provides little protection if the complete decryption key is permanently stored beside the encrypted configuration.

Therefore:

> **The distributed installation alone should not contain everything required to derive the protected runtime configuration.**

Successful authorization from Illuminates.One should contribute information required to unlock or derive access to protected configuration.

A possible future implementation could combine:

```text
installation-specific material
           +
authorization-derived material
           ↓
runtime configuration key
```

The precise cryptographic scheme requires separate security design and review.

M0.1 must not invent proprietary cryptography where established primitives are available.

---

## 17. Copy Resistance

One objective of the authorization, installation identity and configuration model is that copying an entire Lumen research installation to another machine should not automatically create another functional authorised installation.

A copied installation may contain:

- source code;
- containers;
- encrypted configuration;
- service definitions;
- Distribution ID;
- Service Group UUID;
- Illuminates.One public verification key.

Those values alone must not constitute authorization.

Where the installation private key is hardware or OS bound, copying the filesystem should specifically not reproduce the installation's cryptographic identity.

---

## 18. Capability Authorization

The authorization response may eventually contain an authorised capability manifest.

For example:

```text
Moderari   allowed
Praebere   allowed
Trace      allowed
Replay     allowed
Rogare     allowed
Aestimare  unavailable
Fiducia    unavailable
```

This allows the same authorization infrastructure to support future distinctions between:

- research distributions;
- evaluation distributions;
- commercial installations;
- development installations;
- future licensed features.

M0.1 does not need to implement the complete future licensing system, but its authorization protocol should avoid preventing this extension.

---

## 19. Separation of Responsibilities

### Illuminates.One

Responsible for:

- recognising authorised installations;
- maintaining the authoritative installation registry;
- registering installation public keys;
- securely retaining the Illuminates.One authorization private key;
- verifying installation signatures;
- issuing signed runtime authorization;
- controlling authorization status;
- maintaining distribution and installation provenance;
- optionally defining authorised capabilities.

### Servire

Responsible for:

- identifying the service group;
- maintaining the installation cryptographic identity;
- protecting the installation private key;
- generating fresh authorization challenges;
- signing authorization requests;
- communicating with Illuminates.One over HTTPS;
- verifying Illuminates.One authorization signatures;
- maintaining the Illuminates.One authorization lease;
- deriving local runtime authority from valid authorization using established cryptographic mechanisms;
- issuing service-specific short-lived runtime leases;
- renewing service leases while Servire remains authorised;
- unlocking protected runtime configuration;
- controlling service lifecycle;
- validating service startup;
- supervising the service group.

### Individual Services

Responsible for:

- accepting only valid Servire-authorised startup;
- validating the service-specific runtime lease before becoming operational;
- requiring periodic Servire lease renewal while running;
- rejecting invalid, expired, mismatched or replayed service leases;
- consuming configuration provided through the authorised runtime mechanism;
- not independently implementing Illuminates.One licensing or external authorization logic;
- not possessing permanent independent authority to operate.

This deliberately keeps the external trust relationship concentrated in Servire.

---

## 20. Secrets and Distributed Code

No secret embedded in externally distributed source code, containers or binaries should be assumed to remain secret.

This includes:

- API secrets;
- private Illuminates.One signing keys;
- permanent configuration decryption keys;
- master licensing keys;
- hidden passwords;
- hard-coded authorization bypass values.

Public verification information, including the Illuminates.One authorization public key, may be distributed where required.

Private Illuminates.One authority must remain exclusively on infrastructure controlled by Illuminates.One.

---

## 21. Security Boundary

The M0.1 system must recognise an unavoidable limitation:

> **Software executing on hardware controlled by another party cannot be made impossible for that party to modify.**

A sufficiently motivated person with source and machine access could alter checks, patch code, extract locally held material or reconstruct functionality.

The purpose of the M0.1 protection model is therefore to:

- prevent accidental unauthorized use;
- prevent simple copying from creating another functioning installation;
- make circumvention deliberate;
- cryptographically identify authorised installations;
- authenticate Illuminates.One authorization;
- prevent simple replay of authorization exchanges;
- provide provenance;
- maintain control over supported operation;
- protect configuration and operational authority;
- complement contractual licensing restrictions.

It must not be represented as providing absolute tamper resistance.

---

## 22. Relationship to Licensing

Runtime authorization is a technical control.

The research licence remains a contractual control.

The two mechanisms serve different purposes and should reinforce each other.

The licence may prohibit activities such as:

- redistribution;
- unauthorized commercial use;
- removal of notices;
- circumvention of authorization controls;
- extraction or misuse of protected credentials;
- modification intended to bypass licensing restrictions.

Technical design should nevertheless seek to reduce dependence upon legal enforcement.

---

## 23. M0.1 Architectural Rule

For the external M0.1 distribution, the governing rule is:

> **Illuminates.One authorises the installation. Servire cryptographically establishes and maintains that authorization. Servire is the local root of operational trust, controls service lifecycle and access to protected configuration, and issues short-lived runtime leases to individual services. Every protected Lumen service enforces that Servire trust boundary and possesses no permanent independent authority to operate.**

The authorization relationship is protected through complementary mechanisms:

**TLS/HTTPS**  
Protects communication in transit.

**Installation key pair**  
Allows Illuminates.One to authenticate the requesting installation.

**Illuminates.One signing key pair**  
Allows Servire to authenticate the authorization it receives.

**Nonce and short-lived Illuminates.One authorization lease**  
Prevents simple replay and limits the useful lifetime of previously issued installation authorization.

**Servire-issued service runtime leases**  
Propagate authorization into each protected service, bind authority to a specific service and instance, and prevent a service from acquiring permanent independent authority merely because it was successfully started once.

## 24. Future Work

The M0.1 implementation should establish the architectural boundary without prematurely designing the complete commercial licensing system.

Future work may include:

- final cryptographic primitive selection;
- authorization token format selection;
- secure installation provisioning;
- installation key registration;
- TPM/hardware-backed key support;
- operating-system key-store integration;
- key rotation;
- Illuminates.One signing-key rotation;
- installation key revocation;
- service lease token format and validation;
- service lease key derivation/authentication design;
- common runtime trust validation component for protected services;
- service launch assertions;
- service manifest signing;
- capability manifests;
- authorised migration to new hardware;
- offline research licences;
- commercial licence tiers;
- distribution-specific watermarking/provenance;
- tamper evidence;
- secure update mechanisms;
- signing of official Lumen releases.

These should build upon the M0.1 authorization architecture rather than requiring it to be replaced.
