# M0.1 Trace Model Recording and Replay Requirements

## 1. Purpose

This document records the agreed M0.1 requirements for preserving the model used
to create a Vestigare trace and for enforcing that model when Repetere or Fiducia
starts a replay.

M0.1 retains the existing runtime-global model-selection design. It does not add
replay-specific model residency or general per-session model selection. Those
capabilities remain deferred until each session can select and own its model.

## 2. Service Ownership

- Vestigare owns trace evidence and recording metadata.
- Repetere owns replay execution.
- Fiducia owns scheduled replay initiation and result reporting.
- Pontis owns sessions and their association with the global model selection.
- Praebere owns model discovery, selection, reservation, activation, residency
  and release.
- Repetere and Fiducia must use the normal Pontis/Praebere session and model
  lifecycle. They must not load a model directly or bypass global selection.

## 3. Vestigare Recording Requirement

Vestigare must add the authoritative model used to create the trace to the
corresponding `trace_recordings` document.

At minimum, the recording must contain:

```json
{
  "model": {
    "provider": "ollama",
    "name": "qwen2.5-coder:14b-32k"
  }
}
```

The model identity must come from the authoritative Lumen execution path, not
merely from an unverified model value supplied by the client.

The exact model identity may continue to be present in individual trace messages,
but recording-level metadata is required so Repetere and Fiducia do not need to
infer it by decoding message bodies.

If practical within the existing schema, the recording may also retain the
provider's immutable model digest or equivalent identifier. The provider and
exact model name are the minimum M0.1 requirement.

## 4. Repetere Replay-Start Behaviour

The compatibility check must occur when replay actually starts. A check performed
when a replay is configured or scheduled is insufficient because global model
state may change before execution.

Before starting replay execution, Repetere must:

1. Read the authoritative provider and model from the trace recording.
2. Confirm that the recorded model is present in Praebere's authoritative cached
   model catalogue.
3. Obtain the current authoritative global selection, reservation and lock state.
4. Apply the decision rules in section 4.1.
5. Reserve the applicable model for the Repetere replay session through the normal
   Pontis/Praebere lifecycle before sending the first replay request.

Repetere must not directly ask Ollama to load the model. Normal first-execution
activation remains Praebere's responsibility.

### 4.1 Decision Rules

| Runtime condition | Required M0.1 result |
| --- | --- |
| No global model is selected and the recorded model is available | Select and reserve the recorded model for the replay session, then continue normally. |
| The globally selected model exactly matches the recorded model | Reserve the same model for the replay session, then continue normally. |
| A different global model is selected, reserved or locked | Log and display a controlled model-conflict error, and do not start the replay. |
| The recorded model is not in Praebere's cached catalogue | Log and display a controlled model-unavailable error, and do not start the replay. |
| The trace has no authoritative recording-level model metadata | Log and display a controlled missing-model-provenance error, and do not start the replay. |
| Model selection or reservation fails | Preserve the authoritative failure, log and display a concise explanation, and do not start the replay. |
| First-execution model activation fails | Use the normal Praebere activation-failure behaviour, including cancellation of the failed reservation, and mark the replay as failed. |

### 4.2 Model Conflict

M0.1 must not offer to replay a trace using a different active model. Such a run
would not be a faithful replay of the recorded execution.

A conflict error must identify both models. For example:

> Replay requires `qwen2.5-coder:14b-32k`, but the active Lumen model is
> `qwen2.5-coder:14b-16k`. End all sessions reserving the active model before
> starting this replay.

The conflict must leave the existing global selection, reservations, active
sessions and model residency unchanged.

## 5. Fiducia Scheduled-Replay Behaviour

Fiducia must apply the same compatibility rules at the scheduled execution time.
Because no researcher may be present to resolve a conflict, its behaviour must be
deterministic:

- If no global model is selected and the recorded model is available, initiate
  normal selection and reservation for the replay session and continue.
- If the selected model exactly matches the recorded model, reserve it for the
  replay session and continue.
- If a different model is selected, reserved or locked, do not start the replay.
- If model metadata is missing, the recorded model is unavailable, or selection,
  reservation or activation fails, do not start or continue the replay.

For every rejected or failed scheduled replay, Fiducia must record a failed run
result containing a concise reason and the relevant recorded and active model
identities where available.

Fiducia must not change or interrupt the active global model merely to satisfy a
scheduled replay.

## 6. Replay Integrity and State Safety

- A replay may proceed only with an exact provider/model-name match for M0.1.
- Starting or rejecting a replay must not silently change another session's model
  state.
- A rejected replay must not create an active model-execution session.
- Ending or failing a replay must release its own reservation through the normal
  lifecycle without disturbing reservations held by other sessions.
- Errors must be visible to the operator and present in the appropriate operational
  or scheduled-run record.
- Model compatibility control activity must remain outside model context and must
  not be recorded as conversational trace content.

## 7. Deferred Behaviour

The following are explicitly outside M0.1:

- Running a replay concurrently on a model different from the global model.
- Giving Repetere private model residency.
- Temporarily replacing the global selected model for a replay.
- Allowing the researcher to substitute a different model and still treat the run
  as an ordinary faithful replay.
- General per-session model selection and concurrent multi-model lifecycle
  management.

These capabilities should be addressed with the future work in which each session
can select and own its model.

## 8. Minimum Validation

1. A completed trace recording contains the authoritative provider and exact model
   name.
2. Repetere selects and reserves the recorded model when no model is selected.
3. Repetere proceeds when the selected global model exactly matches the trace.
4. Repetere rejects a different selected, reserved or locked model without changing
   existing runtime state.
5. Repetere rejects a trace with missing model provenance.
6. Repetere rejects a recorded model absent from Praebere's cached catalogue.
7. Failed model activation cancels the replay reservation and does not register an
   active execution session.
8. Fiducia records a failed scheduled-run result when the active model differs from
   the recorded model.
9. A rejected scheduled replay does not modify or interrupt active global sessions.
10. Existing same-model multi-session reservation and release behaviour remains
    unchanged.
